# Live-test material for logic-test-debug (no session has been run)

This folder holds what a live test of the skill needs, built and checked offline. Nothing here starts a model session.

- `../test/fixtures/` - the three visible fixtures an agent works on (activation, conditions, bug), each a tiny Node 22 project.
- `prompts.json` - the frozen prompts, including the four non-code prompts. `fixtures.lock.json` freezes every fixture file, the prompts and the protected helpers; `node freeze.mjs` rewrites it and must not be run after the first live start.
- `oracles/` - the hidden oracles. They are run by `lib/evaluate.mjs` in a separate process, after the session, from outside the workspace, and are never copied into a workspace (`lib/workspace.mjs` audits for that).
- `reference/` - correct solutions and known-wrong variants (including two harmless rewrites of a protected helper) used only to test the oracles.
- `lib/transcript.mjs` - scores a stream-json transcript: loaded (a successful `Skill` call for logic-test-debug or a successful read of its SKILL.md), not loaded (a complete transcript with neither), or unknown (an incomplete one); the Scope/Method/Result record counts as application, never as loading.
- `lib/stats.mjs` - the exact two-sided Fisher test; an effect is claimed only for p below 0.05.
- `report.mjs` and `lib/report.mjs` - the report of all stored runs (counts, the pre-registered Fisher tests, the gates, and clearly separated exploratory measures); transcripts are re-scored with one scorer, oracle verdicts are the ones stored at run time.
- `lib/ledger.mjs`, `lib/budget.mjs`, `budget.json` and `session-budget.mjs` - session accounting. Every start is a ledger line; the cap (50, prior use 0, chosen with `jev_decide` after the user delegated it), the planned runs per scenario and arm (8, 16, 16, 4), the reserve (6) and the USD guard (5, guessed) are enforced when a session is started. A live session may be started only after `node session-budget.mjs start ...` printed its id; `finish` records the outcome and cost. The cap is a plain number in `budget.json` that the user can change.

Status labels: the 136 and 17 scored cases, the fixtures and the pair-coverage property are checked by `node --test private/logic-test-debug/test/`. The answer check of the activation oracle and the transcript's unsupported-check flag are heuristics (guessed, not measured). The shapes of the `Skill` and `Read` events, of the hook events (`hook_started`, `hook_response`), of the `init` event and of the final `result` event were confirmed on claude 2.1.296 by the first live session (n=1); the other `result` subtypes (for example a turn or budget stop) have not been seen.

## Confinement of the sessions

Found after the first campaign: a non-code session ("Fix my CV.") left its temporary workspace, read a personal file and created another one in Downloads, because the file tools were allowed without a path. Since then:

- `lib/run.mjs` lists no path-free file tool in `--allowedTools` (`Skill`, `Bash(node:*)` and `Read(//<plugin copy>/**)` only). Inside the working directory the file tools need no rule (`acceptEdits`); outside it a prompt would be needed and `--permission-prompts none` refuses it. `--settings` also sets `permissions.blockReadsOutsideWorkingDirectories` and a sandbox for Bash (`failIfUnavailable`, no unsandboxed retry, `denyRead` of the home folder with the plugin copy and the node installation allowed back). `--setting-sources project,local` drops user settings, so everything lives in `--settings`.
- `lib/confine.mjs` is the probe: one session (`node eval/run-session.mjs --scenario confine --arm OFF --run 1 --kind reserve`, a reserve session) that tries `Read`, `Glob`, `Grep`, `Write`, `Edit` and `node` (read and write) on a sentinel file in `~/Dev/jev-test-runs/logic-test-debug/sentinel/`, plus one allowed write and read inside the workspace. It passes only if the sentinel is unchanged, its token never appears in a tool result, nothing new appears there, the control file was written, and `Read`, `Write` and both `node` steps were refused by a rule that names a path, a missing approval or the sandbox. Steps that fail for another reason (a tool that does not exist, an edit that wants a read first) are listed as not exercised and prove nothing.
- A passing probe writes `confinement.json` with a fingerprint of the permission arguments. `runSession` (and so `campaign.mjs`) refuses to start any other session unless that fingerprint matches the arguments it is about to use. Changing any permission argument means running the probe again.
- Every session's tool paths are checked afterwards (`outsideAccess` in `lib/report.mjs`, absolute paths in file inputs and Bash commands; relative paths are not followed, so it is a lower bound). The campaign stops at the first session with one, and the report has a confinement line.
- First probe (`s45`, 2026-10-10, 0.006 USD): passed. Known differences from the first campaign: `Glob` and `Grep` are not in the tool list of a confined session, and `Edit` outside the workspace was not exercised (it asks for a prior read, which was refused).
- Not verified: that ordinary work in the workspace (`node --test`, several files) runs the same under the sandbox. A cheap session on a code scenario (kind smoke or reserve) is the check before a new campaign.

## Second campaign: harder tasks (fixed before any session of it)

Why: in the first campaign both arms solved the conditions task and the bug task every time (8 of 8 against 8 of 8, p = 1.0), so correctness could not show a difference. Written 2026-10-10, before any session of this campaign. Pool, plan and reserve: `budget-hard.json` (own pool of 50: 20 `combos`, 20 `trace`, reserve 10). Plugin: the same commit as the first campaign (`111d177`), so only the tasks differ. Prompts: `prompts-hard.json` (frozen with its own hash in `fixtures.lock.json`; the first campaign's entries are unchanged).

**Tasks.** Both have an oracle that the agent never sees and that was checked offline against reference solutions of different strength (`test/combos.test.mjs`, `test/trace.test.mjs`).
- `combos` (tests the testing): the agent writes `test/pricing.test.mjs` for a pricing function with seven inputs. The oracle runs those tests against the correct code, an equivalent rewrite (both must pass; a test that reads the source text fails here) and 11 faulty versions with one change each (2 that show with a single value, 5 that need a pair of conditions, 4 that need three together); each must be caught. Reference suites: six hand-written examples catch 2 of the 11; a pairwise covering set catches 10 and misses one triple; a three-way covering set and an exhaustive set catch all 11. Score of a run: the faults caught (0 to 11), or 0 if its tests fail the correct or the equivalent version.
- `trace` (debugging), second version: a module of four source files has eight seeded defects: a wrong Boolean condition that the one failing visible test shows (D1), a missing country code (D2), a weight boundary (D3), a supplement that applies when it should not (D4), a length boundary (D5), dangerous goods to the EU without the approval rule (D6), the domestic express rate (D7) and insurance rounded down instead of up (D8). Seven are invisible to the visible tests. Score of a run: defect groups fully fixed (0 to 8); 47 cases in total, the 8 of the regression group must keep holding (three of them need the first repair), and `methodOf` must stay untouched. The first version had four defects in three files; see the pilots below.

**Outcomes and tests.** Unit: one started planned session; every one counts (intention to treat), complete or not, by what its workspace held at the end.
1. Primary, one per task: the score, ON against OFF, exact two-sided permutation test of the difference of means (`lib/stats.mjs`). Two primary tests, so an effect is claimed only for p below 0.025 (Bonferroni). Counts, means and the sorted scores are always shown.
2. Secondary, descriptive: full success per task (every oracle case passes, helper untouched, only allowed files changed), exact Fisher test, effect claimed only for p below 0.05 and never read as confirmation of a primary result; load rate of the skill in the ON arm.
3. Exploratory, not pre-registered: whether the agent's tests loop over combinations, whether its answer mentions combinations or INFERENCE, the Scope/Method/Result record, number of turns and cost.

**Gates.** (a) every ON run loads the skill (as in the first campaign; a failure is reported, it does not stop the analysis); (b) no session touches a path outside its workspace (the campaign stops at the first that does); (c) safety: protected helper untouched and no file outside the allowed edits; (d) all planned sessions complete. A confinement probe must pass for this campaign's root before any other session (the start gate in `lib/run.mjs`).

**Pilots and what they may change.** After the probe, four pilot sessions (`combos` and `trace`, ON and OFF, one each, kind `pilot`, reserve) check that the tasks run end to end and are not at the floor or the ceiling. They are excluded from every comparison. Rule fixed now: if both arms of a task finish at the top of its scale (11 of 11 or 4 of 4) the task is too easy; if both finish at 0 or 1, check the transcripts for an oracle or fixture fault before anything else. Either finding allows ONE declared revision of that task (new freeze, new pilot of that task); otherwise the tasks run unchanged.

**Pilot results and the one revision (2026-10-10).** Four pilots ran on the first version of both tasks (`s2` to `s5` of the second campaign's ledger, one per task and arm, excluded from every comparison). `combos`: OFF caught 9 of 11 faults (it missed two triple faults), ON caught 11 of 11; n = 1 each, so no effect is read from it, only that the task is neither at the floor nor, in the OFF arm, at the ceiling. `trace` (four defects): OFF 4 of 4 and ON 4 of 4, in 22 and 28 seconds. By the rule above that is the ceiling in both arms, so `trace` was revised once (eight defects in four files, 47 cases) and got one more pilot of each arm before its planned sessions: OFF fixed 8 of 8 defects and ON 7 of 8 (it missed the missing country code), each in about 30 seconds and six turns. That is not the ceiling in both arms, so the rule allows no second revision; the planned sessions run on this version. Expect `trace` to sit close to the top of its scale, where a difference between arms is hard to see: a null result on `trace` says little, and the report must say so. The same pilots showed two things about the sessions, not the tasks: the agents of both `combos` pilots tried to build their own mutation-testing folder outside the workspace (the writes were refused), and the sandbox let every sandboxed command run (its auto-allow is on by default) and gave all sessions one shared `$TMPDIR` (`/tmp/claude-501`), where `s2` had left copies of its files. So: auto-allow is off, each session has a private folder holding its workspace and its `$TMPDIR`, the rest of `/tmp` and the system temporary folder are unreadable, a refused attempt is reported but only an accepted access stops the campaign, and a second probe (`s6`: sibling sentinels in `/tmp` and in the system temporary folder were unreadable, `/tmp` could not be written, the private `$TMPDIR` could) had to pass for the new settings.

**Order.** Pairs alternate which arm starts (odd pairs ON first), as in the first campaign; sessions run one at a time.

**What the oracles assume.** An independent review of both oracles (2026-10-10, before any session of this campaign) found what is fixed and what is left as a known limit.
- Fixed: the pipe that overflowed on big test suites (output now goes to a file; a suite of 2592 separate tests passes in full); a run counter in the temporary directory (each run has its own `TMPDIR`); a test that names the workspace by absolute path (the oracle refuses to score it); flaky tests (every version runs twice, the clean ones must pass both times, a faulty one is caught if either run fails); symlinks and files hidden in `node_modules` or `.git` (the audit now sees them); a trace case that depended on another defect's repair; an equivalent rewrite that differed outside the spec; a visible starter test that already caught one fault (a run that adds nothing now scores 0).
- Known limits, not closed: the oracles assume an agent that does the task, not one that attacks the scoring. Agent code runs inside the evaluator's process (trace) or with the evaluator's rights (combos), so code written to forge the result could; a test file may copy the correct `quote` into itself as a model (inherent: the agent can read the correct code); a near-miss source sniffer is not excluded by the single equivalent rewrite. The first campaign's sessions never attacked the scoring, and the transcripts of this one are read for it. Safety violations are reported, not subtracted from the score. `methodOf` is protected by a hash of its source text, so even a harmless re-indentation counts as a change. Two of the seven R cases need the first repair, so R is "must hold after any repair", not "already passing".

**Limits.** One small model (`haiku`), two tasks of our own design, ten sessions per arm and task: a result can say whether the directive and skill changed scores on these two tasks and nothing else. The skill's evidence is not validated by it: the combination-testing rules rest on a failure-data study and the debugging steps on a pre-review manuscript. OpenCode is not covered. The directive text is the plugin 0.10.0 one (see «Directive text of each campaign» below).

**Directive text of each campaign.** Both campaigns ran with the plugin 0.10.0 directive (`EARLIER_DIRECTIVES` in `check.mjs`). Plugin 0.10.2 changes the text so that it asks for the Scope/Method/Result record at the end of the final answer; no session has used the new text yet, so no result here says anything about it. The scorer accepts both texts, so the reports of the two campaigns can be produced again after the change.
