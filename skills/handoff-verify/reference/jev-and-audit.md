## Jev tool contracts (exact shapes; do not stretch them)
- `mcp__jev__jev_verify` `{"claims": ["..."], "evidence": [{"id": "chunk-0002", "text": "..."}]}` → per claim `verdict` (verified | contradicted | unsupported) + `confidence`. Claims must be concrete, atomic statements. `unsupported` is NOT proof of absence: evidence may simply be incomplete.
- `mcp__jev__jev_compare` `{"passage_a": "...", "passage_b": "...", "aspects": ["..."]}` → `same_fact | contradicts | different_facts`. `different_facts` means "not the same fact", not "absent". The two passages are the only evidence: `same_fact` means they agree, not that they are true.
- `mcp__jev__jev_extract` `{"document": "...", "fields": [{"id": "sha", "pattern": "\\b[0-9a-f]{7,40}\\b", "description": "..."}]}` → picks among **regex** candidates verbatim. Only for paths/commands/numbers/SHAs/versions/ids. `not_found` = the regex matched nothing, not that the fact is absent. It is not a free-form list generator.
- `mcp__jev__jev_classify` `{"items": [{"id": "...", "text": "<≤2000 chars>"}], "classes": [{"id": "handoff", "description": "..."}, {"id": "non-handoff", "description": "..."}, {"id": "manual_review", "description": "..."}]}` for text files written in the session whose names do not match the handoff name patterns. > 0.95 `handoff` → include; > 0.95 `non-handoff` → exclude but list as `excluded: non-handoff (confidence X)`; otherwise list as "possible handoff, unconfirmed". Large files: classify every chunk of the relevant excerpts, not only the first fragment.
- `mcp__jev__jev_gate` `{"request": "...", "claims": ["..."], "evidence": [...], "diff": "<patch>"}` — for a **concrete patch** with claims to check; do not use it to invent a global guarantee from a list of findings. Each claim in it is also filtered with your own strict > 0.95 check. Binding of a gate result: `jevref.py` reads the claim results from the top-level `results` (flat form) or, for `jev_gate` only, from `verification.results` (the envelope the inspected gate implementations return), matched by the exact claim string and the original index, with no recursive search; a response holding both locations, or neither, is an `unknown response shape` and binds nothing. The strict conditions are unchanged and are read where they always were: `same_subject` on the selected result and `subject_at` at the top level. The inspected repository gate and the inspected cached 0.14.1 gate emit neither field, so upgrading to that package does not by itself make a gate claim resolvable: such a claim stays UNRESOLVED (`advice.py` says `protocol_fields_absent`) until a recorded gate response carries both. The patch review and the aggregate are reported apart by `jevref.gate_summary` (also printed as `gate_summaries` by `advice.py`): review `action`/`status`/`reasons`, aggregate `action`/`truncated`, verification `action`, claims matched and strictly resolved; its `holds` is true only for a complete exact claim/result correspondence, every claim `verified` > 0.95 under the strict conditions, an `auto` non-truncated review (a successful review has no `status`; `invalid_response`, `review`/`escalate` or `incomplete_context` do not hold) and an `auto` aggregate. Passing claim results never imply an accepted patch; the summary is an observation only (no version binding, no change of a report status).
- `mcp__jev__jev_screen` is a prompt-injection/content control, not a utility filter and not proof of completeness. Use it on referenced external files if they look untrusted.
- Evidence limits: `jev_compare` passages ≤ 20,000 chars; `jev_extract` document ≤ 50,000; `jev_classify` text ≤ 2,000 per item (64 items). Retrieval order or top-k never proves absence: **walk every chunk and review it for all nine categories**: `work/coverage.json` saying `complete: true` only means that the chunks were produced, it is not a review (the progress ledger never claims completeness either); PASS needs the reviewed `audit` block of "Mandatory audit", and a chunk not reviewed makes the dependent checks UNRESOLVED (say so).

## Mandatory audit (full-report review; a PASS needs it)
ONE audit (`scripts/audit.py`) judges every status: `report.write_report` (the report), `versions.py status` (the delivery gate) and every summary in `handoff.versions[]` (the write summary and each `prefix` / `session_end` evaluation) call it, so the writer and the gate never disagree. The WHOLE report is first validated against `scripts/report.schema.json` (`schema_check.py`, the same validator for the writer and the gate): a malformed report never crashes anything, never PASSes and certifies no delivery (the gate prints `audited_status: null` and the structural count). A PASS needs a COMPLETE audit, otherwise it is UNRESOLVED with the reasons (`binding_summary.audit`: `complete`, `reasons`, `unfinished` counts, `scope`); a confirmed defect keeps FAIL and the unfinished work is still counted; the audit never creates a FAIL and never changes a Jev threshold. `verified_version` answers a different question (the identity of the delivered version) and can hold with an incomplete audit; PASS never means delivery.
- **What the report must hold** (`scripts/report.schema.json`): `scope_exclusions` (a list; an empty list is a valid audited zero, a missing or non-list value is missing accounting) and `audit` = `{"version": 1, ["max_chars"], ["registry"], ["ledger"], "evaluations": [block]}` (`registry` and `ledger` are optional and the report does not choose them: see "Candidates") with ONE block per evaluation (write id + sha256 + `prefix`|`session_end` + `run`; writes with equal bytes, the two modes and the runs share nothing). A block holds `evaluation` (`{write_tool_use_id, sha256, evaluated_against[, run]}`, copied from the `version_ref` of its checks; `null` for a report without version identity), `chunks`, `categories` and `unresolved`.
- **Chunks**: the EXPECTED chunks are re-derived from the real source by the code of `prepare.py` (`prepare.derive`: its source eligibility, sanitization and stream boundaries) and bounded by the REAL window of THIS evaluation (`omissions.source_window` for the write, the mode and the run; the artifacts of `prepare.py` do not change): `prefix` = the chunks up to the write (`versions[].prefix_chunks`); `session_end` = the chunks that hold material BEFORE THE START of the selected verification run (`version_ref.run`; one run after the write is selected automatically, several need the name; the spans of the other runs are generated material, and a later user instruction is source only for the later run); no write = every chunk. A chunk whose text also holds material outside the window (a boundary inside a chunk) is expected and marked `window_partial` in the template: only the records (or the leading blocks of a record) inside the window are evidence, the rest of the chunk is never certified. The report's own list cannot redefine the expected set. Each expected chunk needs exactly ONE record `{index, sha256, reviewed: true, categories: [1..9], basis: {"uuid", "quote"}}` where `sha256` is the hash of that chunk's text (`coverage.json` `chunk_list`) and `basis` is the uuid of a record of that chunk inside the window and an exact quote of THAT record's text. A missing, duplicate, stale, unreviewed or ungrounded chunk, or a review of fewer than nine categories (a shortlist of two is not a review), blocks the PASS. `audit.max_chars` declares a `--max-chars` other than the default 9000; a different value gives different hashes, so a stale review fails closed.
- **Categories**: exactly nine records, one explicit outcome for each category (a tenth or a malformed row is structural unfinished work): `candidates` (listing EXACTLY the ids of the registered candidates of the category: not a subset, no foreign id, no repeated id), or `no_candidate` / `not_applicable`, each with `basis` = `{"uuid", "quote"}` — the uuid of a record inside the window of the evaluation and an exact quote of THAT record (a quote of another record, or of the part of the chunk after the record, does not ground it; a window with no record needs none). A `reviewed` boolean, `complete: true` or nine bare outcomes are not a review.
- **Candidates**: the registry is the one of the SOURCE SESSION: `<first cwd the session records>/.handoff-verify/<session>/audit-registry-<hash8>.json`, derived from the source and never chosen by the report. Preparation establishes it: `prepare.py` in its default run directory creates it (with `--out` it writes nothing else), `audit.py template` / `register` establish the evaluation, `omissions.py prepare-batch --ledger F` and `audit.py template --ledger F` associate an omission ledger with the session. `python3 -B <skill-dir>/scripts/audit.py register --source <session> --file <handoff> --write-id <id> --evaluated-against prefix|session_end [--run <id>] --detail <detail> [--category 1-9] [--quote <quote>]` records a candidate BEFORE the scope filter and the omission scheduling (the registry only grows; a secret-dependent detail is kept by hash only and can never be cleared); `audit.py template ... [--ledger F]` prints the UNREVIEWED block and the expected candidates: it is work to do, not a review. The audit reads the registry and the ledgers of the session ITSELF, and of every other representation of it that the inputs demonstrate (a byte-identical copy or the original of the calls log / of the transcript the report names, `versions.same_session`): their registries are merged (every candidate, established evaluation and ledger association of any of them counts), so an established EMPTY registry of one representation never erases work registered against another, and a malformed or foreign registry of any of them fails closed; EVERY demonstrated representation needs its own established registry (a missing one is unfinished work that no other representation's registry stands in for: `audit.py template --source <it>` establishes it); the registry of an unrelated session is never read. A ledger shared by several sessions counts, for each session, only the obligations whose `identity.source` is that session or a representation of it; a row is excluded only when its source is POSITIVELY another session (`versions.distinct_sessions`: both transcripts readable with recorded session ids and tool uses and no session id in common, or two different OpenCode selectors; a mere failure of `same_session` is not proof), and a row whose source is withheld, missing, unreadable, empty, malformed, metadata-deficient or otherwise undemonstrated still counts. Omitting `audit.registry` / `audit.ledger`, naming another registry (substituted accounting), a registry that is missing, unreadable, of another session or that never established the evaluation, an unreadable ledger, and a session that records no usable cwd all block the PASS; only a registry that was established and holds no candidate is a valid zero. Every candidate applicable to the evaluation (the registry, plus every obligation of the ledgers whatever its state: `valid`, `invalidated` or `unavailable`) needs a disposition the audit DERIVES itself: `present` (a bound, resolved check whose only claim is the canonical absence claim, with the exact material), `excluded` (a valid scope exclusion), `omission` (a validated finding) or explicit unresolved work (`unresolved`: `{"candidate": id}`; counted, never a PASS). A disposition label written by the model clears nothing. A model-written report is never read unsafely: a record that does not match `report.schema.json` (a check whose `id` is a list, a finding whose `type` is an object, a declared version whose `tool_use_id` is a list) is evaluated as an empty record, the structural problem is counted (a PASS cannot survive it, a validated defect among the usable records keeps FAIL), and the writer carries none of its own properties (`status_claimed`, `delivery`, `binding_summary`, ...) from the input. Two checks of one evaluation are one evaluation: the unfinished work is counted once per write / hash / mode / run in the report, the write summary and each evaluation summary.
- **Not evidence**: the stored status, `binding_summary`, `scope_audit`, `coverage.complete`, `source_ranges[].complete`, a `reviewed` boolean alone, a categories-2/9 shortlist and the sha256 of a ledger.
- **Honest limit**: the registry and the ledger are editable files and a hash binds a snapshot only. The audit proves that what was registered is accounted for and that the chunks were reviewed as the report states; it cannot prove that the reviewer discovered every semantic candidate, and that never excuses dropping a registered one.
- `jevref.audited_status` is a low-level helper marked `certifying: false`: only `audit.certify` (the report, the gate, the per-version summaries) turns it into a report status.

## Retry advice
Before the single re-verification of a `jev_verify`/`jev_gate` claim that did not pass, run `python3 -B <skill-dir>/scripts/advice.py --session <the session with the Jev calls>`: for every result that is not > 0.95 with the strict auxiliary conditions it prints a deterministic `advice {code, hint}` read from the REAL result, never a verdict. `fix_fact` (contradicted > 0.95): correct the fact, more evidence will not help; `recheck_fact` (contradicted ≤ 0.95): compare with the source, then correct the claim or add the exact passage; `evidence_off_subject` (`same_subject` < `subject_at`): give the passage about this subject; `remove_unsupported_detail` (unsupported, `details` = numbers, versions, paths or names of the claim absent from the evidence): remove them or add the passage that states them; `add_source_passage` (unsupported otherwise); `add_direct_evidence` (verified ≤ 0.95; `split` true when the claim joins several facts, i.e. two or more parts of three or more words separated by `;` or by and/but/while/whereas/și/iar/dar/însă, never by a bare comma: split it in the same re-verification, one claim per fact with its own evidence); `aux_condition_failed` (verified > 0.95 but Jev did not let the verdict stand on its own: `action` review, or `same_subject`/`subject_at` missing; give evidence about exactly this claim; a server that returns no `same_subject`/`subject_at` cannot pass the strict conditions); `result_mismatch` (the result does not carry the claim that was sent: no verdict advice is given, the check stays unresolved); `no_result` (no usable result: only a transport or `invalid_response` error allows one identical retry, as `report.TRANSPORT_ERRORS`). `protocol_fields_absent` (a usable, correctly identified verify/gate result whose recorded response lacks `same_subject` on the result or `subject_at` at the top level: the strict conditions cannot be met by that response whatever the evidence, so the advice is structural, recommends NO evidence retry (`evidence_retry` false) and does not spend the single re-verification; the check stays UNRESOLVED, the affected required checks are reported UNRESOLVED with this reason, and the user is told that a future run needs a server whose recorded verify/gate responses carry those fields at those locations; nothing is installed or restarted automatically, no package version is assumed to supply them, old results are not retrofitted, and the retry rule is not bypassed). It is distinct from a field that is present but `null` or invalid (`aux_condition_failed`, with the state in `fields`) and from finite off-subject evidence (`evidence_off_subject`), and it comes after the `result_mismatch` and `no_result` guards and before every evidence-focused code. Each advice entry also carries `fields` (the recorded state of `same_subject` and `subject_at`: absent, null, invalid or finite) and `causes`, every coexisting reason in a fixed order (`protocol_fields_absent`, `subject_fields_null_or_invalid`, `evidence_off_subject`, `action_not_auto`, `verdict_contradicted`/`verdict_unsupported`, `confidence_not_above_threshold`); the primary `code` follows the established precedence. `advice.py` also prints `capabilities`: what the recorded responses of the session show, one row per tool, envelope shape and field states with the number of results and calls; every recorded response is judged on its own fields (no majority, no attribution from a package version), and a later response that carries the fields is judged normally and never blocked by an earlier one. `report.py` stores the same `advice` on every bound, unresolved verify/gate check outside an omission pair; it never changes a status, and the retry rule is unchanged (one re-verification, new evidence or a corrected claim, never an identical call).

## Engine: txdiff — events, epochs, states
1. **Event register**: walk every chunk (prefix of the version) and record events `E1…` with `epoch` (position), `type` ∈ request | decision | attempt | failure | correction | validation | blocker | resolution, `aspect` (a concrete noun phrase, e.g. "registry access", "test result of tests/test_billing.py"), the `state` it sets, `uuid`, verbatim quote. Do not compact epochs: keep both the failure and its later resolution.
2. **Final state per aspect** at the version's write time (later event wins within the same source; user > tool > assistant; keep conflicts). The last version also gets a second pass against the end of the session → `stale` findings.
3. **Per-aspect diff**: for each aspect, take the handoff passage that talks about it and call `jev_compare` with `passage_a` = the handoff passage, `passage_b` = the final-state event quote, `aspects` = ["<aspect>"]. `contradicts` > 0.95 ⇒ candidate wrong fact / stale state → confirm with `jev_verify` of the handoff's claim against the evidence chunk (must be `contradicted` > 0.95). `same_fact` > 0.95 ⇒ aspect covered. `different_facts` ⇒ **not** an omission by itself: candidate only.
4. **Omission candidates** (aspect with no handoff passage, or `different_facts`): first apply the **scope filter (R05)** below to ALL candidates; only the candidates it does not exclude continue. For each of them run `python3 <skill-dir>/scripts/omissions.py prepare --source <session> --file <handoff> --write-id <id from versions.py list> --evaluated-against <prefix|session_end> --detail "<one atomic detail>" --source-quote "<exact quote lying inside ONE transcript record>"` (exit 3 means UNRESOLVED, with reasons); it prints the two canonical claims, the source passage and the complete material. Make the ABSENCE call first (below); the SOURCE call is only for candidates whose ABSENCE result qualifies. With several candidates (also across handoffs and versions), prepare them all in ONE call: `python3 <skill-dir>/scripts/omissions.py prepare-batch --spec <file.json>` (`--spec -` reads the same JSON from stdin, no temporary file; `--ledger <file>` records the obligations so a long audit can resume: see "Omissions (R04)"; the per-version preparation is reused between candidates, and the printed `hints` only point at records, they never clear a candidate), where the file is a list of `{"detail", "source_quote", "source", "file", "write_id", "evaluated_against"[, "cwd", "run"]}` (the same values as the flags; flags given on the command line are defaults): it prints a JSON array whose element i is exactly what `prepare` prints for item i (exit 3 if any element is not ok; treat that element as above). Then, ABSENCE-first: (1) `jev_verify` with claim = `absence_claim` (the bare detail, the only claim of that call), evidence = `material` copied verbatim and complete (not a chunk, not a summary). If it is `verified` or `contradicted` make no SOURCE call and report no finding (UNRESOLVED if that result is <= 0.95, `review` or otherwise unresolved). (2) Only if (1) is `unsupported` > 0.95 with `action` auto: `jev_verify` with claim = `source_claim`, evidence = `source_passage` (the several `source_claim`s of candidates with the identical `source_passage` of the same write may share this one call, each claim exactly as printed; `omissions.plan_source` groups them; never inside an OpenCode `execute` wrapper holding several Jev calls). Report a lost_detail finding only if (2) is `verified` > 0.95 and (1) is `unsupported` > 0.95 with `action` auto. Passage difference alone never proves omission.
5. Resolved blockers still shown as active in the handoff ⇒ `stale_state`; active blockers missing ⇒ omission (category 5). Aggregate with the status rules.
