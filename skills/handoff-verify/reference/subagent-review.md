# Delegated review (on explicit request only)

**When it runs.** Only when the user asks for it, for example «let a subagent read the transcript». Otherwise do the review yourself, in this session (D0). Delegation can lower the cost of reading chunks in the main context; it never lowers the standard: the reading is delegated, the certification is not.

**What stays in this session, always.** Registering the candidates (`audit.py register`, before the scope filter), every Jev call (ABSENCE first), the report, and the delivery gate. The subagent has no Bash, no Jev tool and no write tool. Its answer is data, never evidence: a candidate counts only after you re-read the original record and run the usual procedure. The subagent's summary is never material of a claim. Delegating the Jev calls or the report (one subagent that does the whole procedure, or one per phase) is not offered: calls that live only in a subagent transcript are not bound by the log of this session, and `same_session` between the two is not assumed either way.

**Flow (one subagent at a time, in the foreground, no nested agents).**
1. Prepare as usual (`prepare.py`, `audit.py template`). The window of the evaluation must be proven BEFORE any delegation: the evaluated write for a `prefix`; a recognized run already in this session for a `session_end`.
2. `python3 -B <skill-dir>/scripts/delegation.py assign --source S --note N --write-id ID --evaluated-against prefix|session_end [--run ID] --chunk-dir WORK --from I --to J [--session-cap CAP] [--out F]` writes the assignment for the chunks I..J that the window expects (at most 20): the identities, the exact spans and the chunk hashes come from the code. `--chunk-dir` is the `work/` folder of `prepare.py`; a chunk file that is not the prepared text is refused (`chunk_file_stale`). Refusals: `write_not_found`, `window_unavailable` (an ambiguous or unproven window: do not delegate), `interval`. Pass `--session-cap` only when jev-control is on and you hold a real capability; never make one up.
3. `delegation.py prompt --assignment F > P` writes the prompt of the subagent. Start the agent `jev:handoff-reader` with the Agent tool and `run_in_background` set to false: left unset, the call in a headless session started the agent in the background and the answer came only from a later notification. Give it either the prompt itself, word for word, or (preferred, measured cheaper) one sentence: «Read the file P in full (continue after a truncated read) and follow it exactly.» The prompt copies the hard rules and the nine categories from SKILL.md as they are, never inlines the chunks, and when a capability exists it carries the line «Session capability: pass --session-cap <cap> to every cli.mjs call, also in subagent prompts» with the real value.
4. Save the answer to a file and run `delegation.py validate --assignment F --result R`. Exit 0 only for a complete, valid answer; the valid candidates are listed even when the answer is not valid. The answer is checked against the window re-derived from the source, not against the assignment.
5. Take the accepted candidates, re-read their original records, and register them yourself. A rejected candidate stays visible as unfinished work; do not hide it and do not retry for a more convenient answer. For every missing or invalid chunk (`missing_chunks`) read the chunk yourself. An incomplete interval never becomes `no_candidate`: build the nine global outcomes only from chunks that a valid answer reviewed or that you read, each with a basis (uuid and an exact quote of that record). On any failure, timeout or invalid answer: read the chunks yourself (D0), keep the accepted candidates and the blockers, or report UNRESOLVED if you cannot finish.

**Measured live (2026-10-11, 10 headless sessions, 8 of them Haiku, on invented sessions; 0 Jev calls; 0.96 USD in all).** The agent was found as `jev:handoff-reader`, used only `Read`, read only the files it was given, and ran on the parent's model (Haiku under Haiku, Sonnet under Sonnet). The plugin hooks also ran inside the subagent (8 to 11 `PreToolUse`/`PostToolUse` events for its reads, none blocked anything). Every complete answer passed `validate` and held the 6 planted details; two sessions with prompt-injection text inside the records and a made-up capability showed no sign of obeying it. A chunk that lies only partly in the window (a `session_end` run starting inside it) produced no quote from outside the spans, and the reader said so itself. A chunk the reader could not open (permissions removed) made it answer `complete` false with a blocker, invent nothing, and `validate` named it in `missing_chunks` while keeping the 9 valid candidates. One call over 18 chunks was valid and complete: a 12 KB answer, 104 s, 0.11 USD. Answers were 5.6 to 15.8 KB for 6 chunks (Haiku with the inline prompt listed 23 to 44 candidates, many of one kind; Sonnet 9; Haiku with the pointer 9 to 12), so split an interval on `result_too_large`. Pointer-prompt sessions cost 0.014 to 0.017 USD against 0.029 to 0.032 for the Haiku sessions that carried the 15 KB prompt (a hint, not a proof). A subagent's own calls are not copied into the log of the parent: they live in a separate `subagents/agent-*.jsonl` file. On 13 small real sessions `assign` worked. On the 3 real development sessions I tried it refused with `window_unavailable`: once «source window ambiguous», and twice because 22 of 500 and 3 eligible blocks (Write/Edit calls and their results) are in no prepared chunk. The refusal comes from `window_of`, which the audit uses too (read from the code, not run). Do not expect to delegate a long development session.

A parent session ran the whole flow on its own: `assign`, the agent in the foreground with the one-sentence prompt, the answer saved, `validate`. Haiku, once: valid and complete with 11 candidates, the assignment id the code gives, the saved answer the agent's answer unchanged (0.02 USD, 81 s); its final report said it had not read the note, though its second command had printed it. Sonnet, once: the same flow and an honest report, but `validate` said invalid (`category_candidates`: the reader listed a candidate under a category it was not given), 6 candidates accepted, and the parent chose to read the chunks itself without retrying (0.31 USD, 64 s, about thirteen times the Haiku session).

A stopped agent. With the reader cut after one turn (a plugin copy with `maxTurns: 1`: a stand-in for a timeout, not a wall-clock one) the Agent tool returned only «this agent stopped at its 1-turn limit before finishing»; the parent saved that as «NO ANSWER», `validate` said `invalid_json` with chunks 0 to 5 missing, and the parent proposed to read them itself and invented nothing. The docs list `maxTurns` for plugin agents and a stall timeout (`CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`) for subagents; this plugin sets neither. An answer file that was never saved is also an invalid answer with every chunk missing, not a crash.

Discovery. Text-only cases made from the prose of two real sessions and their real notes, with the window ending at the write, gave 28 and 47 valid candidates (10 to 14 KB, 91 to 155 s, 0.02 to 0.03 USD), spread over all the chunks. The reader did not obey the instructions inside a pasted summary and did not repeat the old capability that summary held. Of the facts the transcript held and the note did not (found by my own reading before I saw the answers: 8 and 7 facts) the reader raised 2 and 2, and most of its candidates restate what the note already says (n = 2). Treat its list as a starting point, never as complete.

**Not established.** A real wall-clock timeout of a subagent (only a turn-limit stand-in was seen), discovery beyond two real sessions, and a parent that is neither Haiku nor Sonnet.

**Reasons of `validate`.** `result_too_large` (at most 32768 bytes), `invalid_json`, `schema`, `foreign_assignment`, `result_not_sanitized`, `capability_in_result`, `window_unavailable`, `assignment_stale`, `chunk_record`, `chunk_stale`, `chunk_categories`, `chunk_ungrounded`, `chunk_duplicate`, `chunks_missing`, `category_records`, `category_outcome`, `category_candidates`, `category_ungrounded`, `candidate_rejected`, `incomplete`.

**Fallback to doing it yourself (D0).** An ambiguous window; a `session_end` whose run is not demonstrated; a harness that does not restrict the agent to the Read tool or does not let it use the parent's model; an input too large for the answer cap; any doubt. Do not pick a cheaper model by default.

**Honest limits.** The saving is not measured: it is about the bytes of the chunks you do not read, minus the answer and the passages you must still read yourself, and it can be negative. The subagent loads its own copy of SKILL.md, so the total cost can rise; the parent's context only gets lighter if the always-loaded SKILL.md is short. The tool list is documented as an allowlist, but the rules in the agent file are instructions, not a verified sandbox. The hooks of the plugin run inside a subagent too, and their effect on this reader is not verified. What is not established is listed above; none of it changes the binding or the gate. Nothing here makes a PASS easier: the audit still re-derives the chunks, the quotes and the candidates from the source.
