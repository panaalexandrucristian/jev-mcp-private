## Orchestrated run (`orchestrate.py`): live comparison, 2026-10-12 (measured, n = 1 to 2, one fixture)
Setup: headless `claude -p`, model claude-haiku-5-5, real Jev calls, a fixture of four tiny files whose three note bullets are stated exactly, so every claim has direct evidence; the note is about 58k tokens of context per turn, far below the 500,000 guard, so this says nothing about scaling above it. Turn 1 = write the note and verify it; turn 2 (`--resume`) = one approved change (a fourth bullet), a recorded Edit, then verify the new version. Tokens are the sums over the assistant turns of the stream (cache read + cache creation + uncached input + output; output is under-counted by the stream); the dollar figures are the CLI's own and are noisy (cross-session cache hits, cause not verified).
- Turn 1, baseline (the documented flow): 21 turns, cache read 1,505,469, cache creation 98,975, total 1,604,611, 0.083 USD: PASS, complete audit, `verified_version`.
- Turn 1, orchestrated (the prompt asks for the Orchestrated run), three runs, all PASS with a complete audit and `verified_version`: 17 turns, cache read 993,125, creation 98,729, total 1,091,994, 0.075 USD; 14 turns, 787,838, 85,606, 873,555, 0.033 USD (with the literal-path rule in the section); 16 turns, 960,579, 92,154, 1,052,853, 0.045 USD (final code). That is 19% to 33% fewer turns and 36% to 48% less cache read than the one baseline run (n = 1 against n = 3, not a statistical result).
- A first pilot on a fixture with an unstated extra fact (`current release tag`) stayed UNRESOLVED: the model registered that fact as a candidate and the ABSENCE check came back `unsupported` at 0.61 (review). Not comparable; it shows that a candidate which cannot be cleared keeps the audit incomplete.
- Turn 2: in all four sessions (baseline; orchestrated; orchestrated with the literal-path rule, twice) the Edit was recorded and the new version was NOT verified (turns 13 / 13 / 7 / 10, 1.54M / 1.52M / 0.69M / 1.07M tokens; in the last one the model also skipped `edit-preflight` and made the Edit directly): `audit.py template` and `orchestrate.py prepare` refused with `source window ambiguous: an event names a script of this skill that cannot be resolved`. Cause: the model had called skill scripts through a shell variable (`SK=...; python3 $SK/scripts/audit.py`) earlier in the same session; `omissions.py` cannot resolve such a path, so it cannot tell which events belong to the earlier verification run, and it fails closed for every later version of that session. The documentation rule (literal absolute paths) was not followed in either run that had it (0 of 2). The same cause is the likely one behind the `source window ambiguous` refusals recorded for real development sessions; it is not shown here to be the only one.
- What the orchestrator did right in turn 2: `edit-preflight` hash-checked the verified bytes and made the backup, the change was one recorded Edit, the old report was rejected by the gate (`needs_reverification`), and `prepare` refused the new version with the reason and a hint instead of a silent half-state. No threshold, window rule or approval was relaxed.

## Variable expansion in the shell classifier (`omissions._expand_vars`), 2026-10-13 (measured)
Why: in the live sessions above, every skill-script path built from a shell variable (`SK=/abs/...; python3 -B $SK/scripts/x.py`) was `unknown`, and one `unknown` event makes the source window of every later version ambiguous. Now a variable is expanded only when the same command assigned it, earlier on its straight line, a plain absolute word that certainly ran (see the docstring for the exact limits); everything else stays `unknown`.
- Over all 1,140 local transcripts (24,892 Bash commands, before and after on the same records): 319 `unknown` became `yes`, 7 `no` became `yes` (genuine reads and runs of skill files through a variable, which had counted as source), 1 `unknown` became `no`; no `yes` changed, 48 transcripts have a changed command. The big session ba5998aa, which edits the skill itself, goes from 29 to 19 `unknown` commands; the rest (mostly `python3 - <<EOF` code that names a script, relative paths, `$(...)`) is not touched, so this change alone does not clear that session's `source window ambiguous`.
- The five live update sessions that had stayed unverified (baseline and orchestrated, 2026-10-12) all refused `orchestrate.py prepare` for version 2 before; all five prepare it now (replay on the real transcripts, no model, no Jev). With only the leading-run rule two of them still refused (an assignment after other commands, `D=$HOME/x; ls "$D"; SK=/abs; python3 $SK/...`), which is why the rule follows the straight line of the command.
- Live: the blocked session C5 was resumed once with the fixed scripts (8 turns, 0.89M tokens, one `jev_verify` call on four claims) and ended PASS, complete audit, `verified_version` for version 2 (sha 143810e0), confirmed by running the gate again from outside. One session, resumed with a note that the scripts had been fixed: it shows the repair, not the unprompted behaviour.
- Tests: `test_shell_vars.py` (14 tests, exhaustive over 11 positions x 12 value kinds x 4 uses = 528 commands, so strength t = 3 without sampling; 15 of 15 mutations of the new code caught).

## Source-window classifier: a measured improvement loop, 2026-10-13 (measured unless a label says calculated)
Why: the update turn of a real verification run hit `source window ambiguous` in 4 of 24 unprompted live cycles, so the loop looked for the next classifier change that could be shown to help. Setup per round: a change in a separate worktree, offline tests (exhaustive tables, mutations, replay of every Bash command of every local transcript, 25,120 commands up to a fixed cut-off), live cycles (headless sessions, model Haiku 5.5, real Jev, a fixture of four tiny files; a cycle is turn 1 = write the note and verify it, turn 2 = one approved bullet and verify the new version; n = 3 cycles per round), then an independent review by three reviewers on different models, read-only, that had to agree unanimously on whether the test was valid and whether to keep the change. No agreement meant the change was dropped.
- Kept: the variable expansion above (`_expand_vars`) and one correction found by the first round: a command substitution (`$(..)` or backticks) in a skill-script path is `unknown`, not `no`, because what it prints is not known: the substitution is replaced by the placeholder `$-` (no command can assign that name) and the more severe of the two answers wins. A command with a real here-document is exempt (the text after it is data); a quoted `<<` or a here-string is not one. The replay changes 0 command classes with this correction, so its value is a hole closed after a probe, with a measured frequency of zero in these transcripts. Tests: `test_shell_subst.py` (new).
- Dropped, each by the rule above: a rule for an assignment inside an `&&` chain (rounds 2 and 7), here-document bodies treated as data or as shell text of their own (rounds 3, 4, 5 and 7). Every version had a new case where it would call a command harmless that was not: for example `xargs` or `bash -s` run what they read, a variable changed after the body started, `builtin export SK=...` and a function that sets the variable inside the chain. Round 6 was run offline only and has no live cycle.
- Live results (turn 1 verified / turn 2 verified, of 3 cycles, median model turns per cycle): control, baseline 3/3, 2/3, 24; second control, same code, run later 2/3, 2/3, 29; round 1 3/3, 2/3, 28; round 2 2/3, 1/3, 29; round 3 3/3, 3/3, 32; round 4 3/3, 3/3, 31; round 5 3/3, 2/3, 24; round 7 3/3, 2/3, 23. With n = 3 these detect a regression, they do not show a benefit. The difference in turns between the first control and later rounds (24 against 28 to 32) also appears with the unchanged code (29), so it is time or noise, not code (calculated).
- Replay of version-2 `prepare` on the 19 live cycles that kept an update state: the kept code refuses 3 and accepts 16 (`results/replay-r7-prepare.txt` of the loop folder). The 3 refusals are the shapes listed below.
- Live failures that the classifier did not cause: a Jev score of exactly 0.95 (not above it), an extra omission candidate rated 0.94 to 0.95, the model reading the source file in the same command as a skill script (the source window excludes that), the model editing the note before `edit-preflight`.
- Cost: 48 sessions, 4.38 USD (calculated from the per-cycle cost fields of the CLI).
- Suite on the final code: all tests OK, 2 skipped, on Python 3.14 and 3.12.
- Not fixed, on purpose: (1) an assignment in a `&&` chain, and a Python line `for ...:` in a here-document body that empties the variable table; each is about 1 of 24 unprompted cycles, and any new attempt must handle `builtin`, functions and wrapped mutators in the chain rule and judge every here-document body with the variables and directory at the point of the body. (2) `cd DIR && SK=/abs; python3 $SK/...` stays `unknown` because the assignment is not certain to have run; a rule "possible values, join the classes" would fix it but extends the fail-closed rule and needs its own round. (3) A Python here-document that imports a skill module is invisible to the classifier, `mutation_target` and `tool_io` still split here-document bodies as part of the command, and `NAME+=value cmd` is read as a command word (all old behaviour). (4) Untested: a reminder text that tells the model to read the file a new bullet relies on in a command of its own (it caused 2 of 24 failed update turns); it is not part of this change. (5) One fixture, one small model, n = 3 per round, and no unprompted live cycle on the exact final code (the live pool was spent).
