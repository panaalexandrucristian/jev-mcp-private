# Integration

## Commands and files

- `/jev:jev-control on|off|status|threshold <x>` (`commands/jev-control.md`) runs `private/jev-control/cli.mjs`; `/jev:jev-done` and `/jev:jev-locate` have explicit control branches; `agents/jev-locator.md` carries the control rules.
- Code lives only in `private/jev-control/` (`cli`, `actions`, `state`, `budget`, `client`, `contracts`, `options`, `protocol`, `search`, `done`, `receipts`, `hook`, `measure`, `run-session`, `test/`, `fixtures/`, `results/`). The upstream files (`src/`, `skills/jev`, `README.md`) are untouched.
- Edits to private jev-flow files are limited to seams: `scripts/jev-flow-hook.mjs` delegates to the control hook first; `private/jev-flow/hook.mjs` stands the flow down while the mode is on; `private/jev-flow/gate-run.mjs` and `policy.mjs` accept an optional policy (threshold, no 0.8 floor, budgeted call); `hooks/hooks.json` registers one more event, `SessionEnd`, on the same adapter. With the mode off, everything behaves as before.

## jev-flow and handoff-verify

While the mode is on for a session, jev-flow's directive, hints and Stop redirects are suppressed even with `JEV_FLOW=on`; its payload guard, state tracking and the denylist notice stay. `handoff-verify` is unchanged: its stricter obligations (strict `> 0.95`, per-file approval, never executing code from a handoff) apply on top, and its Jev calls count in the shared budget.

## Hooks (no blocking hook)

The hook is the only place that sees the real `session_id`, so it is where the session is proven. `UserPromptSubmit`: for a `/jev:jev-control` prompt, or an explicit natural-language request (the phrases of the skill description, English and Romanian, matched without case or diacritics), it creates the session's **capability** (`<session key>.<secret>`; the secret is stored 0600 in the session state, compared in constant time, never in `state.json`) and puts `Session capability: pass --session-cap <cap> to every cli.mjs call, also in subagent prompts.` into the model's context; with the mode on, an ordinary prompt starts a new request (budget counters) and prints the one-line reminder (at most 400 bytes) with the capability, while a mode command does not start a request. The helper accepts, in this order, an explicit `--session-id`, `CLAUDE_CODE_SESSION_ID`, or the capability; a capability that contradicts the environment's id is refused (`identity_conflict`); with none of them there is no identity and nothing is selected by guessing (a CLI of another session never adopts the most recent session). Subagents are given the capability by the parent in their prompt. A request phrased in a way the hook does not match gets no capability: the helper then refuses and the user is asked to run `/jev:jev-control on`.

`SessionStart`: after a compaction (`compact`, the same live session) the compact rules (R09: `private/jev-control/rules.mjs`, at most 1500 bytes with the loading line) and the capability are re-injected; `startup`, `resume`, `clear`, `fork` and any unknown source switch the mode **off** and rotate (remove) the capability, so nothing carries over and the mode must be requested again. `SessionEnd` (registered in `hooks/hooks.json`, any reason) switches the mode off and removes the capability. The hook runs no Jev call and no test and never blocks. State also expires after 30 days.

## What is demonstrated offline, and what is left for R02

**Demonstrated offline** (tests with hook payloads labeled as fixtures, a fake stdio MCP server, and the installed Claude Code 2.1.288 binary inspected, not run): the capability is created by the hook, proves only its own session, and is refused when wrong, foreign, malformed, expired or in conflict with the environment (`private/jev-control/test/{state,hook,cli}.test.mjs`); two sessions in one repository stay apart; a subagent process given the parent's capability shares the parent's state; `startup`/`resume`/`clear`/`fork`/unknown sources and `SessionEnd` switch the mode off and rotate the capability, `compact` keeps it; `hooks/hooks.json` registers `SessionEnd`. The binary's hook schema contains the `SessionEnd` event (reasons `clear`, `resume`, `logout`, `prompt_input_exit`, `other`) and the `SessionStart` sources `startup`, `resume`, `clear`, `compact`, `fork`. `claude plugin validate` does not check hook event names, so a pass proves nothing about them.

## Data

Only sanitized fragments of the current repository go to Jev (`sanitize.mjs`; no `.env`, keys, credentials or tokens), and `.jev-flow-denylist` is honored: a refused repository means the mode refuses to start. No credential is read from files; the server uses the environment only, as in jev-flow.

**Live, R04 (dev S2 and dev S3, ledger 8 and 9):** (9) confirmed: with the R03 hook line both sessions ran `cli.mjs on` as their first action and never called the Skill tool; the `Read` of `skills/jev-control/SKILL.md` that the line and the command ask for was refused in both (`permission_denied`, reason `workingDir`: a path outside the working directory is not granted, D27 has no Read allowance and `--add-dir` is not an allowed flag), so the protocol reached the model only through the hook line, the `on` result and the helper's error messages. (10) confirmed: without the format the S2 model needed seven invalid `decide` results and two permission refusals to produce a valid batch, modelled the order as a first-step choice (top score 0.93-0.94, never above 0.95) and ended without doing the task; the S3 model tried `search --help` and piped `search` into `head`, which makes the helper an ordinary action that grants nothing. `cli.mjs help [command]` and `<command> --help` now print the batch format and the search form without a session, the `next` line after `on` and the activation text name them, and a refused Read does not end the session; the effect is unmeasured until R05. Whether an interactive session, where the user can grant the Read, behaves differently is unknown.

**Live, R05 (dev S4 and dev S2 at 0.90, ledger 10 and 11):** (11) confirmed: `run-session.mjs launch --threshold 0.90` reaches the helper (`on` printed `threshold 0.9`, `threshold_source env`, and every S2 `decide` carried 0.9), and a threshold given by the environment is overridden by a `--threshold` the model passes (neither session passed one). (12) confirmed: the `order` kind clears the next task only (a task that depends on an unfinished one scores lower: update-greeting 0.90 right after the rename, 0.92 with the evidence that the rename had broken the greeting), so an ordered batch is decided again after its plan items; the S2 model did the last task (the changelog) without a plan item. (13) confirmed: a `decide` followed by `; rm -f <file>` is not a genuine helper call (S4: four of four), so it grants nothing and `measure.mjs` sees no decision; a Write outside the working directory (`/tmp`) is refused in these headless runs. The batch file therefore goes in a new file in the working directory (for example `jev-batch.json` when the name is free; an existing file is never overwritten and only the file the model created is deleted), `decide` runs alone and the file is removed with a lone `rm -f` in its own command; `measure.mjs` treats a batch file as helper input only when the transcript proves it (a confirmed Write that created it; a genuine `decide --file` of the same request and agent context bound at its start to that very version, with a successful selected or ordered result naming only its options; nothing of unknown effects, not even `node --test`, in between; and a lone `rm [-f] <path>` that removed it afterwards: a file left in the tree is an edit). The effect of that wording is unmeasured.

**Live, R06 (dev S1 and dev S2 at 0.90, ledger 12 and 13):** (14) confirmed: with the R05 help a session ran all ten `decide` calls alone, wrote each batch to a new file in the working directory, executed only the plan items (`rename` 0.96, `greeting` 0.93) and stopped with `Incomplete:` when the last order scored 0.84 (below 0.90); `launch --threshold 0.90` again reached the helper (`threshold_source env`).
