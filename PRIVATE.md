# Private Jev plugin mirror

This private repository tracks [`jkudish/jev-mcp`](https://github.com/jkudish/jev-mcp) while adding private packaging for Claude Code and OpenCode. The MCP process still runs the public `@jkudish/jev-mcp@latest` package.

## Repository topology

- `upstream` fetches `https://github.com/jkudish/jev-mcp` and has pushing disabled.
- `origin` points to the private `panaalexandrucristian/jev-mcp-private` repository.
- `main` is the only long-lived private integration branch. Merge upstream into it; never rebase or force-push it.
- The `jev` skill comes from upstream (`skills/jev`, shipped since v0.9.0). This repository adds only the plugin packaging and sync files below, and no upstream-owned file is modified, so upstream merges stay conflict-free.

Branch protection is optional. On private repositories it may require a paid GitHub plan, and required reviews can prevent a sole developer from merging their own synchronization PR.

## Authentication

Configure non-interactive private Git access before installing either plugin:

```sh
gh auth login
gh auth setup-git
```

## Claude Code

Install at user scope:

```sh
export CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1
claude plugin marketplace add panaalexandrucristian/jev-mcp-private
claude plugin install jev@jev-private --scope user
claude plugin list
claude plugin details jev
```

Use `--scope project` or `--scope local` instead when appropriate.

Update or remove it:

```sh
claude plugin marketplace update jev-private
claude plugin update jev@jev-private
claude plugin uninstall jev@jev-private --scope user
```

## OpenCode

Clone the private repository and load the plugin from its directory:

```sh
git clone https://github.com/panaalexandrucristian/jev-mcp-private.git ~/.local/share/jev-mcp-private
```

Add the clone's absolute path to the `plugins` array in `~/.config/opencode/opencode.json` or `opencode.jsonc`. Replace `/Users/you` with your home directory:

```json
{
  "plugins": ["/Users/you/.local/share/jev-mcp-private"]
}
```

Restart OpenCode (`opencode service restart` for the background service), then check:

```sh
opencode plugin list
opencode mcp list
```

Update with `git -C ~/.local/share/jev-mcp-private pull`, then restart OpenCode. Remove it by deleting the path from `plugins`.

Do not use `opencode plugin add 'github:panaalexandrucristian/jev-mcp-private#main'`. On OpenCode 2.0.12 it fails with `NpmInstallFailedError: git dep preparation failed`, because this repository carries the MCP server's npm dependencies. Loading from the directory needs no build, and no `package.json` changes that would conflict with upstream.

The plugin preserves an existing OpenCode MCP server or skill named `jev` instead of replacing it.

## Handoff verification

The private plugin also ships `handoff-verify` (`skills/handoff-verify/`, `jev:handoff-verify` in Claude Code). It loads automatically when you ask Claude Code to write, update or check a handoff/handover note, and verifies the note against the session transcript with Jev: lost details (omissions) and wrong facts (decisions, numbers, dead paths, stale state). A finding counts only with a bound Jev result above 0.95; anything Jev cannot settle above that threshold is reported as UNRESOLVED, never as PASS. It never executes code from a handoff and sanitizes text before sending it to Jev. Worked examples are in `skills/handoff-verify/examples/`.

It runs in Claude Code and reads Claude Code session transcripts; the OpenCode plugin does not register it. It can also verify, retrospectively and from Claude Code, a handoff written in an OpenCode v2 session: pass the explicit selector `opencode:<session-id>` (the default database `~/.local/share/opencode/opencode.db`) or `opencode-db:<absolute-db-path>#<session-id>` wherever the scripts take a source or session (`versions.py list --source`, `omissions.py prepare --source`, `versions.py status --session`, `jevref.py list --session`, `prepare.py`); a session is never guessed. The adapter (`scripts/opencode.py`) opens the SQLite database read-only (`mode=ro`, `PRAGMA query_only=ON`) and normalizes the session in memory only: it writes no export or intermediate file, and nothing read from a session is executed. Mapped: user and assistant text, `write`/`edit` (Write/Edit), `shell`/`bash` (Bash), `patch` (`*** Add File` becomes a Write; an `*** Update File` section becomes an Edit only when an earlier successful write/add/exact edit of that session supplies the base and every hunk applies exactly once and in order; Delete, Move, a non-exact hunk, an unknown base, conflicting `filePath`/`path` values or overlapping mutations of one path give a version marked `content not recoverable` with the reason), and Jev calls (direct `jev:jev_<tool>` / `jev_<tool>`, or an `execute` call with exactly one completed inner `tools.jev.jev_*` call, not truncated, whose returned JSON `tool` equals the inner tool; payload from `state.structured`, then `state.result`, then the concatenated `state.content`; every other `execute` stays unbound). Events are placed by each tool block's top-level `time.created` / `time.completed`. Limits: only v2 sessions (legacy `storage` sessions and child sessions are not read); reasoning, synthetic, system, compaction, agent and model messages are not source text; OpenCode `read` results and the current disk are never an edit base, so many patch updates stay `content not recoverable`; Bash discovery of notes written by shell commands is redirect-only as for Claude Code; a tool block without a valid top-level `time.created` is not placed (no event, version or Jev binding; the message time is never a substitute), and a call without a recorded completion time has no successful result; and the `execute` rule accepts the code as the model wrote it without inspecting it, so a single Jev call wrapped in other JavaScript is accepted on the strength of the returned `tool` field alone (a residual provenance risk of the rule decided by the user). It needs `python3` and accepts the Jev tools under either name (`mcp__jev__*` from a direct MCP config, `mcp__plugin_jev_jev__*` from this plugin). The OpenCode support has offline fixture tests and a read-only test on the local OpenCode database, and has not been exercised with live Jev verifications.

Layout since plugin 0.9.1. `skills/handoff-verify/SKILL.md` (21,329 bytes, was 101,389) is the entry point that loads with the skill: the trigger, the checklist, the hard rules, the categories, the statuses, the command flags, the limits and the loading rules R0–R7. Those rules tell the model to open in full, before the actions each governs, one of five files under `skills/handoff-verify/reference/` (`prepare.md`, `opencode-sessions.md`, `jev-and-audit.md`, `candidates.md`, `report.md`); a reference that cannot be read completely means UNRESOLVED naming the file, never a continuation from memory. The split is lossless: `skills/handoff-verify/scripts/split_manifest.json` cuts the frozen 0.9.0 text (`scripts/baseline/handoff-verify-skill-0.9.0.md`, 101,389 bytes, a test fixture that is never read at run time) into 20 blocks of whole lines, says which file holds each block and declares the two hand-written additions (the loading section and one sentence on reads of the reference files); `python3 skills/handoff-verify/scripts/split_skill.py check` and `scripts/test_split_lossless.py` check it byte for byte. Limit: it is not known whether anything outside this repository quotes a heading or a line number of the old single file; the manifest maps every old line range to its new file. Measured in bytes only: the part loaded with the skill is 79% smaller, a full run reads 3.7% fewer bytes without OpenCode and 2.3% more with it. The effect on results was checked on one live pair (Haiku 5.5, one omission case): the same findings and gate state as the 0.9.0 text, no statistics. The baseline file ships in the npm tarball because `package.json` lists `skills`; the npm version stays unchanged.

Measured in the sealed final evaluation (7 headless sessions on new synthetic fixtures, Claude Sonnet, 10 notes each): triggered on 7/7 handoff requests and 0/28 unrelated ones; omissions confirmed 8/12 (RO) and 3/9 (EN), the rest UNRESOLVED; fact defects 22/28; 0 false alarms on paraphrases and clean notes; 0 invalid PASS. Blocker omissions (0/7) and stale state (2/7) are the weak spots, because Jev scores them near the threshold. The small sample is synthetic and was not measured on real handoffs. The development history and the evidence are in the separate `handoff-skill-lab` repository (`results/SUMMARY.md`). The plugin-prefix support was added after that evaluation and has unit tests only.

## Jev flow

The private plugin also ships `jev-flow`, an adaptive coding workflow on top of the eleven existing Jev tools. It adds no MCP tool and does not modify the upstream `jev` skill. The full contract is in [`skills/jev-flow/reference/workflow.md`](skills/jev-flow/reference/workflow.md); the design is in `docs/jev-flow-design.md`.

| Piece | Claude Code | OpenCode |
| --- | --- | --- |
| Skill | `jev-flow` (route directive injected on every prompt) | `jev-flow` (same directive through the `context` hook) |
| Locate code in an isolated subagent | `/jev:jev-locate <question>` | `/jev-locate <question>` |
| Real checks, `jev_gate` (through the gate runner), final report | `/jev:jev-done [criteria]` | `/jev-done [criteria]` |
| Read-only locator subagent | `jev-locator` on `haiku` | `jev-locator` (inherits, or `JEV_FLOW_LOCATOR_MODEL=provider/model`) |
| Hooks | `hooks/hooks.json` | `private/jev-flow/opencode.mjs` |

Claude Code picks up `skills/`, `commands/`, `agents/` and `hooks/hooks.json` from the plugin automatically; update the plugin as above. OpenCode loads the flow from `opencode-plugin.js`; `git pull` and restart. If any OpenCode capability is missing, only that feature is disabled and one `[jev-flow]` line is logged; the `jev` MCP server and skill are registered first and keep working unchanged.

Local helpers (Node 22 and Python 3 standard library only):

```sh
node scripts/jev-candidates.mjs --root . --query 'regex flag normalization' --limit 5
git diff HEAD | node scripts/jev-candidates.mjs --sanitize --root .
node scripts/jev-gate-run.mjs --root . --list-hunks
node scripts/jev-gate-run.mjs --root . --claims /tmp/claims.json --check '["npm","test"]'
git diff HEAD | node scripts/jev-gate-payload.mjs --list-hunks --root .   # diagnostics
node scripts/jev-gate-payload.mjs --root . < /tmp/jev-gate-input.json     # diagnostics
python3 scripts/jev-flow-metrics.py --session <id> --cli claude|opencode --format markdown
python3 scripts/jev-flow-metrics.py --runs runs.json --format markdown
node private/jev-flow/ab/preflight.mjs
```

The A/B manifest `private/jev-flow/ab/tasks.json` has its oracles marked `not_ready` and no seed; `preflight.mjs` refuses to start the experiment until both are ready.

### Activation and settings

By default, in every session and repository where Jev is enabled, the Claude Code hooks add a short route directive at session start and on every prompt (load `jev-flow`, delegate broad discovery to `jev-locator`, finish code changes with `/jev:jev-done`), and repeat the delegation directive at every 4 exploration calls in a request (4, 8, 12, …). This replaced the earlier advisory default after the Android A/B runs, where the advisory plugin produced no Jev calls and no subagents (`docs/jev-flow-findings.md`, F1). OpenCode sends the same directive through its `context` hook. Blocking stays opt-in (`JEV_FLOW_STRICT`, below).

| Variable | Effect |
| --- | --- |
| `JEV_FLOW=on` | Opt-in switch (also `1`/`true`). Without it: no directive, hints or `Stop` notices/redirects, even with `JEV_FLOW_STRICT=1`. The credential and denylist guard is always active. `/jev:jev-locate`, `/jev:jev-done` and the gate runner stay available on demand. |
| `JEV_FLOW_STRICT=1` | `Stop` redirects once per snapshot to `/jev:jev-done` (below). |
| `JEV_FLOW_LOCATOR_MODEL` | Claude Code: `haiku` (the default in `agents/jev-locator.md`), `sonnet`, `opus` or `inherit` (the parent's model); applied to each `jev-locator` delegation by a `PreToolUse` hook through `updatedInput`. An invalid value is ignored with one notice. OpenCode: `provider/model[#variant]`; unset or invalid, the locator inherits the parent model and the setup notes it once. A configured model is not a cost guarantee: inheriting is fine when the parent already runs the cheapest model. |

`/jev:jev-done` runs the **gate runner** `scripts/jev-gate-run.mjs`: the model writes only claims with evidence ids; the runner collects the diff against the session baseline (new non-ignored files included), runs the `--check` commands itself, reads the cited excerpts, pairs every claim with its own evidence, splits a patch that exceeds one `jev_gate` call into a batch of parts, calls `jev_gate` itself through the jev MCP server on stdio for every part of the batch (only a contradicted claim stops it early) and prints one aggregated report (at most 8 KB): a semantic `verdict`, an operational `status`, the `outcome` that decides the exit code, per-part and per-claim verdicts and the coverage; the agent answers once from it, without re-running for a more favourable verdict (round 3, R5). Payloads never pass through the model (`docs/jev-flow-findings.md`, round 2, R1). Completion needs every part accepted on the same snapshot, and the report says when verification was partitioned. The candidate helper runs `jev_rerank`/`jev_find` the same way when the ranking rule applies (R3) and prints only up to 5 compact hits (path, lines, sha256, score, reason; at most 4 KB), in lexical order marked as not semantically ranked when Jev is unavailable; the locator has no Jev tool, and the parent keeps doing independent work while it runs, in the background when the CLI allows it (round 4, R7). `--full` prints the helper's whole diagnostic object (candidates, map, payload) for tests and debugging only. The hooks hint whenever a read or grep repeats what the locator already returned (R2).

| Runner setting | Effect |
| --- | --- |
| `JEV_FLOW_MCP_COMMAND` | The jev MCP server command as a JSON argv array (no shell), for example `["node","/path/to/dist/index.js"]`. Default: `["npx","-y","--package=@jkudish/jev-mcp@latest","jev-mcp"]`, as in `.claude-plugin/plugin.json`. |
| Credentials | Inherited from the environment only (never read from `~/.claude.json`): `OPENROUTER_API_KEY`, `TYPESAFE_API_KEY`, `JEV_API_KEY` + `JEV_API_BASE_URL`, a Cloudflare token + `CLOUDFLARE_ACCOUNT_ID`, or `AI_GATEWAY_API_KEY`. With `OPENROUTER_API_KEY` and no `JEV_PROVIDER`, the server gets `JEV_PROVIDER=openrouter`. None: `Jev unavailable; gate not evaluated` (exit 3). |
| Limits | Handshake 120 s, each call 300 s, 8 MiB per server message (a larger message, complete or not, ends the session); checks 900 s by default (`--check-timeout`), at most 8, output kept as the first 8,000 + last 32,000 characters with a visible cut marker; excerpts at most 400 lines; summary at most 8,192 characters (per-occurrence detail dropped first; overall claim verdicts and counters always kept); after a part fails for good, one reconnection for the next part. |
| Checks | `--check` takes a JSON array of strings, run as argv without a shell (`'["npm","test"]'`). Any check that exits non-zero, times out, cannot start or has an unknown exit code prevents acceptance (`checks_failed`), whatever Jev answers; the receipt records every check and `Stop` re-checks them. |
| Retries | One retry with identical input after a transport failure, a JSON-RPC invalid response or a result the flow rejects as invalid (`interpretGate` route `retry_or_unavailable`; for rankings, an unusable `jev_rerank`/`jev_find` answer); a closed server is reconnected for it, or the retry is reported as not executed. A contradiction or a valid answer below the thresholds is never retried. |
| Exit codes | `0` accepted, `2` review/escalate/contradicted/checks failed/not accepted, `3` unavailable or disabled, `4` invalid input or not ready, `1` internal error. |

### Opting a repository out: `.jev-flow-denylist`

Put an optional `.jev-flow-denylist` at the repository root. Syntax is a gitignore subset:

- `#` comments and blank lines are ignored;
- `*` matches within one path segment, `?` one character, `**` any number of directories;
- a leading `/` anchors to the repository root (a pattern with any other `/` is anchored too), otherwise the pattern matches a name at any depth;
- a trailing `/` matches a directory and everything below it;
- matching is case-sensitive, like git;
- there is no `!` negation (such lines are ignored and reported) and no character classes (`[` is literal);
- a line that is exactly `*` disables Jev for the whole repository.

```text
# Never send these to Jev
/secrets/
fixtures/**/customer-*.json
*.sql
```

With `*`, nothing from the repository is sent to Jev: the agent runs the local checks and reports `Jev disabled for this repo; gate not evaluated`. In Claude Code a PreToolUse hook denies Jev calls in that repository, and also any Jev call whose payload contains a recognizable unredacted credential. In OpenCode the same rule throws in `tool.hook("execute.before")`; whether that throw blocks the call on 2.0.12 is not verified. A refused `jev_gate` is recorded first as a failed attempt, so it supersedes an earlier accepted gate; if that record cannot be written (busy lock, permissions, full disk), the call is still refused and a notice names the error code.

These files are always excluded and cannot be re-included by any pattern: `.env`, `.env.*` (including `.env.example`), `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `id_rsa*`, `id_dsa*`, `id_ecdsa*`, `id_ed25519*` (including `.pub`), `.npmrc`, `.pypirc`, `.netrc`, `.pgpass`, `.git-credentials`, `.aws/credentials`, `credentials*.json`, `service-account*.json`, `google-services.json`, `GoogleService-Info.plist`, `local.properties`, `keystore.properties`, `signing.properties`, `*.mobileprovision`.

Diffs, logs and candidate fragments are redacted with `[REDACTED:<kind>]` markers (PEM private keys, AWS, GitHub, `sk-`/`sk-ant-`/`sk-or-`, Slack, Google `AIza`, JWT, `Authorization: Bearer`, and assignments to names such as `api_key`, `secret`, `token`, `password`, `storePassword`, `keyPassword`, `private_key`). Bare assignment values are redacted too (for example `password=huntertwo`), except clear code references such as `options.token`. Diff sections that touch an excluded or denylisted file (Git-quoted paths are decoded), or whose paths cannot be parsed, are dropped entirely. Lines that still look like secrets are omitted and reported. This is best effort: a regex cannot recognize every secret.

### Strict mode: `JEV_FLOW_STRICT`

By default the Claude Code `Stop` hook only shows a notice when code changed without an accepted `jev_gate` on the final snapshot. "Accepted" means the latest gate call of the current request (unfinished, failed and locally refused calls included) returned a complete, consistent `auto` result for exactly the claims it was sent, meeting the flow minimums (confidence and `safe_to_apply` ≥ 0.8, composite ≥ 0.7), with the snapshot unchanged during the call and since. A well-formed `auto` that only misses those minimums is not retried; the agent asks the user. Set `JEV_FLOW_STRICT=1` in the environment that starts Claude Code to let it block such a stop once per snapshot and redirect to `/jev:jev-done`. It honors `stop_hook_active` and never blocks a final message that asks the user a question (last non-empty line ends with `?`), starts its last non-empty line with `Incomplete:`, or contains `Jev unavailable; gate not evaluated` or `Jev disabled for this repo; gate not evaluated`. In OpenCode, strict mode only affects `/jev-done`: the command adds the plugin's gate status for the current snapshot and request and instructs the agent not to report completion without an accepted gate. This is an instruction, not enforcement; nothing blocks a completion message, because OpenCode 2.0.12 offers no hook at that boundary (no equivalent of the Claude Code `Stop` hook).

### Local state and checks

In Claude Code the flow stores metadata only (paths, hashes, ranges, counters, request numbers, timestamps, exit codes) in `~/.cache/jev-flow/<repo-hash>/<session-hash>/`, removed after 30 days. It never stores code, diffs, prompts, logs or Jev responses: at `Stop`, a direct gate verdict is re-read from Claude Code's own transcript, and after a restart the gate is unknown. The OpenCode adapter keeps its own state in memory. Set `JEV_FLOW_CACHE_DIR` to move the cache.

The gate runner adds, in both CLIs, a per-session secret `receipt.key` (0600, created at session start, never printed), `baseline.json` (HEAD and the paths already changed at session start, with content hashes) and signed receipts `receipts/<id>.json`. A receipt covers the whole batch and holds metadata only (snapshot and diff hashes, request and attempt ids, per-part numbers, actions or states and verdict codes, coverage counters, the aggregated verdict, status and outcome, claim hashes, check command hashes and exit codes, timestamps) and an HMAC-SHA256; `Stop` and the OpenCode gate status count a runner result only when its receipt verifies for the current session, request, attempt and snapshot. **Threat model:** this stops a model from inventing, editing or replaying a gate result. A process running as the same user that can read the key or modify the runner, the cache or the server is out of scope.

Checks for changes to the flow:

```sh
node --test private/jev-flow/test/
node --test private/jev-control/test/
npm test
claude plugin validate .
node -e "import('./opencode-plugin.js').then(m=>console.log(typeof m.default.setup))"
git diff --stat private-main -- src skills/jev README.md package.json package-lock.json test
```

Known limitations: the state lock is never broken automatically, not even when its owner process is gone; until it is removed the flow treats the session state as unknown and never approves, and the `Stop` notice names the lock file (after checking that no hook of that session is running, delete `~/.cache/jev-flow/<repo-hash>/<session-hash>/lock`, or the same path under `JEV_FLOW_CACHE_DIR`, by hand); OpenCode V2 registration, hooks and permissions are feature-detected but not verified at runtime; OpenCode commands are registered only when `command.list` lets the plugin rule out name collisions; the locator's OpenCode permissions are not set, so in OpenCode its lack of Jev tools and its background launch are instructions only (one setup diagnostic says so); OpenCode strict mode is an instruction only; Claude Code test results are normally unknown because the Bash tool response has no exit code; Claude Code behavior beyond `claude plugin validate` needs a live smoke test on 2.1.283.

**Threshold.** Default `0.95`, strictly `>` on the raw number a tool returns (never a tool's `likely`/`auto`/`action` label, which mean `>=`), valid in (0.5, 1); a session value (`/jev:jev-control on <x>` or `threshold <x>`) beats `JEV_CONTROL_THRESHOLD`; an invalid value gives `0.95` and one notice; a change affects later decisions only. Eligibility is an independent `jev_noul` probability per option (files: `jev_rerank` relevance); near-equal top scores (gap < 0.02) or exclusive options go to successive `jev_decide` selections (at most 6, each accepted only with confidence `> T`); nothing eligible gives at most two expansion rounds with genuinely new material, then a question to the user (headless: a report starting `Incomplete:`); nothing below the threshold runs without the user's recorded approval; Jev unavailable gives one identical retry, then "Jev unavailable".

**Budget.** At most 10000 MCP `tools/call` attempts per user request (`JEV_CONTROL_BUDGET_LIMIT` overrides; 25 before 0.7.3), from every source (model, subagents, helpers, gate parts, tie-breaks), retries included, reserved before each send; the server's own provider calls are reported "unknown". Only the user can raise it: `budget approve --message` needs words that are an authorization **about the budget** (not a quoted refusal, question, condition or quotation, not an unrelated instruction, and a bare «yes» only with the question it answers, `--question`; «Use Jev.» mentions a word without granting the raise) for at most the increment they state (a stated zero, fraction or negative raises nothing) (a total such as «to 30 calls» is the difference to the current limit; an ambiguous number is refused), once per user sentence; the audit applies the same rule to the user's real messages, and `approve` must name the option it approves.

**What Jev reads.** The whole sanitized concrete action of every option (target and arguments in full, never a prefix) goes to Jev as its own context item; a batch that does not fit one call is split over several, a tie-break whose material does not fit stops without choosing, and an action sanitizing cannot show whole is never scored. Receipts and state keep hashes only. Activation is not refused for such transports; the server is not instrumented.

**State.** Metadata only (ids, hashes, scores, counters; never code, prompts or Jev responses) in `~/.cache/jev-control/<repo-hash>/<session-hash>/`, removed after 30 days; set `JEV_CONTROL_CACHE_DIR` to move it. Decision receipts (HMAC under a per-session key) carry the full provenance (options with the action's tool, target and argument hashes, precondition and evidence fingerprints and raw scores, plan items, Jev calls) and authorize exactly the planned action, with its arguments, once (`receipt verify`; a later step of a plan needs its own evidence unchanged); they prove the helper's metadata and what was authorized, not that an action ran; the same threat model as the gate runner's receipts applies. The session is proven by the identity Claude Code exports or by a per-session capability the hook injects (never by "the most recent session"); a new session, a resume, a clear and `SessionEnd` switch the mode off.

## Explain clearly

The private plugin also ships `explica-clar` (`skills/explica-clar/`, `jev:explica-clar` in Claude Code, `/jev:explica-clar`): a mode the user switches on, in which every explanatory reply of the session follows eight rules (summary first, few chunks, one real example, an analogy with a stated mapping, one flat diagram, signalled key points, wording matched to the reader, a short understanding check). It never switches itself on and does not trigger on ordinary questions.

Switch it on with `/jev:explica-clar` or a request such as «explică clar», «explain clearly» or «explică pe înțelesul meu». Switch it off with e.g. «oprește explica-clar» / «stop explaining clearly»; ask whether it is on with e.g. «explica-clar este activ?» / «is explica-clar on?». A new session starts with it off. An explicit instruction of the user (shorter, more technical, no diagram) outranks it. Since 0.13.4 it replies in English, also when the user writes another language, in a style based on ASD-STE100: short sentences with one idea each, words from a community copy of the Issue 9 vocabulary (not the official PDF), and the technical part of a reply is called «Technical data». The style is always on while the mode is on, so there is no separate switch for it.

It is instructions only: no hook, command, script or state file, so the persistence through the session is an instruction to the model, not a mechanism. It is Claude Code only: `opencode-plugin.js` does not register it. The sources and figures of each rule are in [`skills/explica-clar/reference/evidence.md`](skills/explica-clar/reference/evidence.md), not in `SKILL.md`, so the instructions loaded into the session stay compact (as `jev-control-mode` and `jev-flow` keep their details in `reference/`). The research comes from education and health-communication studies, read as abstracts and search summaries, not full papers and not software documentation. Measured on 2026-10-14 with Sonnet and five questions (git rebase, undo a commit, Android rotation, a REST API, port 8080), one reply per case, checkers that read word forms and not meaning (`ste_lint.py`, `ste_vocab.py`, kept outside the repository): replies of subagents that read the skill file had 8 structure violations (sentence or paragraph too long, contractions) with the old text and 0 with the new one, and a mean of 22.4 and 8.6 distinct words outside the vocabulary. In 34 real `claude -p` sessions (the skill installed as a project skill, no tools) two identical runs of the new text gave a mean of 7.8 and 9.8, so a difference below about 2 is noise; renaming «Technical details» to «Technical data» removed the word «details» from 5 of 5 replies (it was in 5 of 5) and did not lower the total. After «no STE» in a second turn the reply stopped following the style, with or without a line that names the command (one session each). Whether it triggers only on request, persists through a long session or improves how well a reader understands is unverified. The offline test is `node --test private/explica-clar/test/`.

## Logic, tests and debugging

The private plugin also ships `logic-test-debug` (`skills/logic-test-debug/`, `jev:logic-test-debug` in Claude Code): rules for reading Boolean conditions, testing combinations of conditions and debugging in a fixed sequence, each rule marked CLEAR (a measured effect in its source), DESCRIPTIVE (observed or proposed, no outcome test) or INFERENCE (not in any source). The rules come from three sources: Baron et al. (EASE 2024, 205 professionals, reading time of Boolean expressions with negations), the NIST combinatorial-testing material by Kuhn (failures triggered by few interacting conditions; the 2004 paper itself was not read) and Maleti and Nel (SACLA 2025, a seven-step debugging model from six lecturers; a pre-review manuscript with no outcome test). The sources, pages, numbers, exceptions and guardrails of every rule are in [`skills/logic-test-debug/reference/evidence.md`](skills/logic-test-debug/reference/evidence.md), not in `SKILL.md` (at most 90 lines).

**Activation.** Automatic, on code prompts only. In Claude Code, `scripts/jev-flow-hook.mjs` loads `private/logic-test-debug/hook.mjs` by a guarded dynamic import on `UserPromptSubmit` (the hook command, its 10 s timeout and `hooks/hooks.json` are unchanged); when a local check, with no model call, finds the prompt to be about writing, changing, reading, testing or debugging code, it adds one directive of about 300 characters to `additionalContext`, joined to any context the other subsystems produced. Other prompts, other events and a failing or missing new module add nothing and leave the existing output unchanged. In OpenCode, `opencode-plugin.js` sets `private/logic-test-debug/opencode.mjs` up in its own try/catch after the flow: it registers the skill beside `jev` and queues the same directive in a `prompt` hook that a `context` hook delivers in every model request of the turn, until the next prompt of the session clears or renews it. Each OpenCode capability is feature-detected and degrades with one fixed diagnostic and no prompt text, and the steps depend on each other: a failed skill registration (or an existing skill with the same id) disables the directive, because it would name a skill that is not there, and without the `context` hook the `prompt` producer is not registered; the existing components are never touched, and the flow's read-only locator subagent gets no directive.

**Why a directive.** In the Android A/B runs a skill chosen only by its description, with one hint per request, was never loaded in 2 of 2 headless runs (`docs/jev-flow-findings.md`, F1). After the directive fix the skill loaded unprompted in 1 of 1 run, but the change combined several parts, so the directive's own contribution is not isolated, and the new check is not validated by it.

**The local check** (`private/logic-test-debug/check.mjs`) is lexical, in English and Romanian: an affirmative coding or debugging intent (an action word with programming context in the same clause, or a standalone «debug»/«depanează»), or a code artifact (a fenced block in a code language or with recognisable syntax, a stack trace or compiler diagnostic, a source file name or inline code together with a request word; a source file name in the same clause also counts as programming context for a request verb such as «repair» or «implement»). Negated intent (also «I don't want you to write code»), quoted words, an explicit limit to prose and a translation or quotation add nothing, and neither does a request about a CV, a recipe, a poem or a video whose only code-like words are ambiguous ones (program, script, method, function, python, cod). Known false positives remain, for example «Develop a training program for new sales hires». Stack traces and compiler output are matched line by line with bounded patterns (an earlier version was quadratic: a 64 KiB prompt of one long path-like word took 2 to 5 s; it now takes about 1 ms, measured). It rejects non-string input and anything over 64 KiB (65,536 UTF-8 bytes) and returns no directive when its 25 ms cooperative budget has expired; synchronous code cannot be preempted, so no hard wall-clock guarantee is claimed. It cannot understand natural language: false matches and misses remain possible (for example «Debug my sleep schedule» matches).

**Switch.** `JEV_LOGIC_TEST_DEBUG`, read from the same environment as `JEV_FLOW`: absent means on; `on`, `1` or `true` (trimmed, case-insensitive) mean on; `off`, `0`, `false`, an empty value and every unrecognised value mean off. Unlike the opt-in `JEV_FLOW`, the default is on, because automatic activation was the requirement. Off skips only the new directive (both hosts) and the new OpenCode registration; the skill files, manual access and every existing component are unchanged, and `JEV_FLOW=off` does not turn it off.

## Android UI step

The private plugin also ships `android-ui-step` (`skills/android-ui-step/`, `jev:android-ui-step` in Claude Code): when the model drives an Android emulator or device from the shell, one command, `ui-step.mjs`, taps a label (or swipes, or presses Back), waits until the layout stops changing and prints a one-line-per-element digest of the new screen; `--shot <file>.jpg` also saves a 540 px JPEG. It replaces the sequence `adb shell input tap` + sleep + `android layout` + `android screen capture`. The skill stands next to the user's own `android-cli` skill and does not edit it (that skill is not maintained here, an update can overwrite changes); its description asks the model to load both.

**Where things live.** `skills/android-ui-step/SKILL.md` and `scripts/` (`ui-step.mjs`, `ui-digest.mjs` for the digest, `img-shrink.mjs` for the JPEG, which uses `sips` on macOS); tests in `skills/android-ui-step/scripts/test/` (`node --test skills/android-ui-step/scripts/test/*.test.mjs`, 56 tests, offline: a fake device injected into `step()` and fake `android` / `adb` commands for the CLI). **Measured on 2026-10-12** (Sonnet 5.5, headless, confined, recorded screens of one app instead of a device, so observations and not rates). ## Compact handoff

The private plugin also ships `compact-handoff` (`skills/compact-handoff/`, `jev:compact-handoff` in Claude Code): when the user asks for a handoff, two commands of one program, `make_context.py` (`--marker`, then `--current <marker>`), turn the transcript of the current session into a folder with `HANDOFF.md`, `blobs/` and, when the session itself began from a handoff, `parents/`, which a new session reads. `HANDOFF.md` begins with all the instructions for the new session (an exact `offset:limit` reading plan, what the markers mean, the four-point answer it must give, the rules) and then holds the transcript: the messages complete; a tool call over 800 characters, a tool result over 300 and any tool call that only reads are replaced by a marker line with a 100-character preview, and their full text is in `blobs/`. The skill hands a session over without `handoff-verify`'s verification (the user switches that skill off in their own settings); nothing in it calls Jev, a model or the network.

**Where things live.** `skills/compact-handoff/SKILL.md` and `scripts/` (`make_context.py` the command, `compact_context.py` the compaction and its checks, `prepare_all.py`). `prepare_all.py` runs the `prepare.py` of `skills/handoff-verify/scripts/` with its two verification exclusions switched off inside the process (no file of that skill changes): those exclusions remove every turn that touched the skill's files, which in a session about handoff-verify hid 29% of the assistant answers (49% of their characters) from an earlier output (measured, one session, first-50-characters matching). Tests: `node --test skills/compact-handoff/scripts/test/*.test.mjs` (30 tests: the package, the Python self tests of 590 and 267 cases, which hold exhaustive tables for the length limits (96), the read-only rule (42) and the cut mode (56), and an end-to-end run on an invented transcript). They are not in the CI workflow, as for `android-ui-step`: the CI job runs the upstream tests and the handoff-verify suite.

**OpenCode (0.13.1).** `make_context.py --opencode DB.sqlite [--session ID] OUTDIR` turns one session of OpenCode 2.0.x into the same kind of folder: `scripts/opencode_source.py` reads the rows of `session_v2` and `session_message` read-only (`mode=ro`) and renders them as the records the existing compaction, round-trip check and reading plan already process. With the marker steps, `--current` also searches OpenCode's database (`$XDG_DATA_HOME/opencode/opencode.db`, else `~/.local/share/opencode/opencode.db`; `--opencode-db` names another file) and refuses unless exactly one session across the Claude Code transcripts and OpenCode contains the marker; an existing database that cannot be read stops the command, and `--no-opencode` skips the OpenCode search (the skill tells the agent to report the error first). Left out: the model's reasoning (encrypted and text). In blobs: the `recent` text of each compaction and every image (a `file` block with a base64 data URI; the marker shows mime, name and length). Whole in the file: user and assistant text, the compaction summary, system and synthetic texts. A tool error shows as `[tool_result ERROR] type: message`, a shell result carries its exit code and the truncated flag. The same sanitizer as for Claude Code runs on texts, tool inputs and text outputs; image data is not sanitized and not scanned for secrets (the sanitizer rewrote all 18 images of one session, 12,552 redactions). The introduction of an OpenCode handoff names the reading tool of both agents, the source session and what was left out; the start command printed is `opencode --prompt "..."`. Sessions kept only in OpenCode's legacy tables (`session`, `message`, `part`) are not supported. `--cut` and `--with-subagents` do not apply. Claude Code output did not change (HANDOFF.md of four recorded sessions identical in size).

**Prompts sent through the SDK (0.13.2).** In blob mode, a user record that the session file marks `promptSource` `sdk` (a prompt sent by a program, `claude -p` or the SDK; the council relays its prompts to its members this way) goes to a blob when it is longer than 300 characters, except the first and the last such record of the session, which stay whole (the role and rules, and the task being worked on). The records are found by uuid in the `.jsonl` (`sdk_uuids_of`): a record with another or no `promptSource`, a sidechain, an `isMeta` record, a compaction summary, a record with an `origin` kind and a record with a tool result never moves. The marker preview is `[user] sdk: ` and the first 80 characters, and the introduction gets two sentences, only when something moved: a marker also stands for a prompt that the session marks as sent through the SDK, and the answers of the user quoted in such a prompt are in its blob. `--cut` and the OpenCode path are unchanged. A person who runs `claude -p` once by hand has one such prompt (first and last), so nothing moves; a session that is resumed by hand with `claude -p --resume` loses the inline text of its middle prompts (it stays in blobs, byte for byte).\n\n**Checks and behaviour.** Every run ends with a byte-for-byte check: expanding `HANDOFF.md` with its blobs gives the prepared text; with `--cut` (one file, no blobs, the long records cut and the rest not kept) every message is identical and every cut a true prefix. Paths inside a handoff are relative to its folder, so a folder can be copied or moved whole. A parent handoff (a `Read` of a `/tmp/handoff-*` file among the first tool calls) is copied whole into `parents/`; the absolute paths in the introduction of a parent made by an older version are made relative in the copy only. Output goes to `/tmp/handoff-<id>-<date>-<random>/` (temporary) or, with `--keep`, to `~/.claude/handoffs/`. Subagent transcripts are left out unless `--with-subagents`.

**A named OpenCode session (0.13.3).** `make_context.py --list-opencode [--opencode-db PATH] [--limit N] [--match TEXT]` lists the sessions of OpenCode's database (the same default file and read-only opening as `--current`), newest update first, at most N (default 15), one line each: `<id> | <date and time> | <N> msgs | <directory, home as ~> | <title cut at 80 characters>`, and a last line `shown N of M sessions[ matching "TEXT"]; database: PATH`. `--match` keeps the sessions whose id, title or directory contains the text (case-insensitive). Only the number of messages is read, never their content; a missing, unreadable or legacy-only database is an error, and no other option goes with it. `opencode_source.py` also lists the titles in the error for several matching sessions. The skill section «A named OpenCode session» tells the agent to list, pick the session the user named (skipping forks unless asked), run `--opencode <database> --session <ID>`, and give the start command of both agents, with no `sqlite3` and no hand-made SQL. Nothing changed in the handoff of a Claude Code or OpenCode session.

**A smaller note in blob mode (0.13.6).** Four changes, all lossless (`--cut` is unchanged and every check of the round trip still compares the whole text): (1) an inline record starts with `[id user]` or `[id assistant]`, where id is the first 8 characters of its uuid instead of all 36 (longer only when two uuids of the session would then look alike; the header of the file declares the length, the blobs keep the whole record, and the byte-for-byte check and the OpenCode self-check compare both sides with the ids cut to that length); (2) a whole line of 200 or more characters that occurs 8 or more times in the inline transcript (the standard sentence of a message from another session is 541 characters and occurs 11 to 23 times) is given once in the header and stands in the transcript as a line made only of a mark, a number and the mark (`¤1¤`), and `read_out` and the check put it back; (3) the preview in the marker of a tool call or tool result no longer starts with the role label that the bracketed kind already gives; (4) the preview is on one line (a line break and the blanks around it become one space instead of `⏎`), and the preview of a tool call whose input is a JSON object with a text as first value reads as text (`[tool_use Bash] cd /x && …; description: …`) with the same number of characters of content. The two limits of the legend (200 characters, 8 times) are a choice made from the measured distribution: with 80 and 3 it took table rows and sender tags, with 200 and 3 it took quotes from a council that occur 2 to 4 times. Not done on purpose: shorter previews (calculated 5 to 7% more, but with a risk of lost detail) and moving more text to blobs, because the rounds with the moved peer messages and the first chunk showed that a reader does not open a blob by itself.

## Provider configuration

Neither plugin stores provider credentials. The Jev MCP process inherits its environment, including supported variables such as:

- `JEV_PROVIDER`
- `JEV_MCP_MODEL`
- `OPENROUTER_API_KEY`
- `TYPESAFE_API_KEY`

Set these outside the plugin. Do not add secrets to either manifest.

## Synchronizing upstream

### Manual synchronization

From a clean `main` branch with the configured `upstream` and `origin` remotes:

```sh
scripts/sync-upstream.sh
```

The script fetches upstream commits and tags, fast-forwards from private `origin/main`, and merges `upstream/main`. It never pushes. On conflict, inspect and resolve the merge, run the printed checks, and push `main` and tags manually.

### Scheduled synchronization

The `Sync upstream` workflow runs every Monday at 06:17 UTC and can be dispatched manually. It mirrors upstream tags, merges new commits into a `sync/upstream-<sha>` branch, runs the repository checks, and opens or updates a pull request to `main`. It never pushes a merge directly to `main` and never auto-merges.

Enable the repository setting that allows GitHub Actions to create pull requests.

The workflow normally uses `GITHUB_TOKEN`. If upstream changes `.github/workflows`, add a fine-grained repository secret named `SYNC_TOKEN` with contents, pull-request, issues, and workflow-file permissions. Without it, the workflow fails rather than dropping those changes.

Merge conflicts and missing workflow permissions create or update the single issue `Upstream sync needs manual action`. Follow its recorded SHA and recovery instructions, or run:

```sh
git switch main
scripts/sync-upstream.sh
# Resolve conflicts if necessary.
npm ci
npm run typecheck
npm run build
npm test
git push origin main
git push origin --tags
```
