Finish the current code change with the jev-flow completion procedure. Extra criteria from the user: $ARGUMENTS

**jev-control branch.** If `jev-control` is on for this session (`node "${CLAUDE_PLUGIN_ROOT}/private/jev-control/cli.mjs" status` prints `"mode":"on"`), run the **same** procedure through the control helper instead of `scripts/jev-gate-run.mjs`: steps 1–5 are unchanged (hunks are listed with `jev-gate-run.mjs --list-hunks`, which is local only), but in step 5 run
`node "${CLAUDE_PLUGIN_ROOT}/private/jev-control/cli.mjs" done --claims /tmp/jev-claims-<something>.json --check '["npm","test"]' [--check ...]`.
**Headless runs (R07):** a Write outside the working directory (`/tmp`), a heredoc and a JSON with braces and quotes on the command line are refused there, and a helper file left in the repository would be part of the diff. So, instead of the `/tmp` file of step 4 and the `--claims` of step 5, Write a NEW file `jev-claims.json` in the repository root (never overwrite another file) holding the claims object of step 4 and, optionally, `"checks": [["npm","test"]]` (argv arrays, run without a shell, after any `--check`), make no further edit and run `node "${CLAUDE_PLUGIN_ROOT}/private/jev-control/cli.mjs" done --claims jev-claims.json` ALONE (`cli.mjs help done` prints the same recipe). The helper reads the file, validates it, removes it BEFORE the snapshot and prints `claims_removed` and `claims_sha256` (that is not acceptance: only the `outcome` is); do not remove it yourself. A claims file with another name, in a subdirectory, tracked, ignored, a symlink or run from another directory is refused and left alone; a file outside the work tree (`/tmp`) and `-` are read as before and never removed.
It sends every `jev_gate` part with `auto_accept` equal to the session threshold `T` and accepts a part only when each decision confidence (claims, `safe_to_apply`, rubric confidences) is **strictly above `T`**, with no 0.8 floor (`composite_floor` and the tool's other policies stay); every part's attempt, retries included, is counted in the shared budget of 25 (source `gate`); at the limit the run stops as `unavailable` with a budget message, and you ask the user. The report, its `outcome`, the receipt and the rules of steps 6–7 are the same. An edit after the run changes the snapshot and invalidates the verification (`snapshot_changed`). Without the control mode, ignore this paragraph.

The gate runner `scripts/jev-gate-run.mjs` does the heavy work: it collects the final diff (against the session baseline, new non-ignored files included), runs the checks you name, reads the excerpts you cite, sanitizes everything, keeps every call within the `jev_gate` limits (splitting into parts only when needed, each part bound to the snapshot), calls `jev_gate` itself through the jev MCP server for **every part** of the batch (it stops early only at a contradicted claim) and prints **one aggregated JSON report**: a semantic `verdict`, an operational `status`, the `outcome` that decides the exit code, each part's action and reason codes, each claim's overall verdict, the coverage and the limits. **Never build or copy a `jev_gate` payload yourself, and never call `jev_gate` directly for this procedure.**

1. **Freeze the snapshot.** Make no further edits during this procedure. If you must edit, start again from step 2: earlier results no longer count. Do not write helper files inside the repository (that changes the snapshot); put the claims file in a temporary directory outside it.
2. **Check the opt-out.** If `.jev-flow-denylist` contains a line `*`, do not run the runner's gate: run the repository's real checks yourself and report **"Jev disabled for this repo; gate not evaluated"** with their results.
3. **List the hunks** (identifiers only, no bodies):
   `node "${CLAUDE_PLUGIN_ROOT}/scripts/jev-gate-run.mjs" --root . --list-hunks`
   It returns `hunks` (`id`, `path`, `header`), the diff base (`session_baseline` or `head_fallback`), `unattributed` (changes already present when the session started, left out of the gate), `preexisting_mixed` (files that were already changed and then changed again; included, but the earlier changes cannot be separated), `unevaluated` (binary files, submodules) and `omitted` (content the sanitizer would remove).
4. **Write the claims file** (for example `/tmp/jev-claims-<something>.json`): one claim per acceptance criterion or check, concrete enough to be judged from its evidence alone (for example "`parseFlags` rejects an empty value and returns `E_EMPTY`", not "the bug is fixed"), each with the ids of its support:
   ```json
   {
     "request": "the user's request, verbatim",
     "claims": [
       {"text": "parseFlags rejects an empty value and returns E_EMPTY", "evidence": ["hunk-2", "caller"]},
       {"text": "npm test passes", "evidence": ["cmd-1"]}
     ],
     "excerpts": [{"id": "caller", "path": "src/cli.ts", "lines": [40, 62]}]
   }
   ```
   - `hunk-N` (or `file:<path>` for all hunks of a file): the diff fragment that implements the claim;
   - an excerpt id: real surrounding code the claim depends on, as `{id, path, lines: [first, last]}`; the runner reads the lines itself (do not pass `text`);
   - `cmd-N`: the output of the Nth `--check` below (every claim about tests, builds or checks cites one).
   Every hunk must be covered by some claim. Do not pass `diff`, `commands`, `tests` or `evidence`: the runner refuses them.
5. **Run the runner once**, naming the repository's real checks (test, build, typecheck, lint) that exist here; the runner runs them itself on the frozen snapshot and captures their real output and exit code. Each `--check` is a JSON array of strings, run as argv **without a shell** (no pipes, `&&` or redirections; to use a shell, say so explicitly, for example `'["sh","-c","npm run build && npm test"]'`):
   `node "${CLAUDE_PLUGIN_ROOT}/scripts/jev-gate-run.mjs" --root . --claims /tmp/jev-claims-<something>.json --check '["npm","test"]' [--check '["npm","run","build"]']`
   For a long suite, run it in the background and wait for it (`--check-timeout <seconds>`, default 900). Do not run the same checks separately first. Starting the runner for a gate already replaces any earlier gate result, even if this run then fails. Wait for the complete report: the runner evaluates every part before it prints anything.
6. **Read the aggregated report once.** It has two separate dimensions: `verdict`, the semantic result (the most severe part: `contradicted` > `escalate` > `ask_user` (a `review`) > `needs_evidence` > `accepted`; `null` when no part was evaluated), and `status`, the operational result (`snapshot_changed` > `checks_failed` > `unavailable` > `ok`). `outcome` is the one that decides the exit code, in this order:
   - `contradicted` (exit 2) → stop and ask the user, quoting the part, the claim numbers (`c`) and the numbers;
   - `snapshot_changed` (exit 4) → the work tree changed during the run; the verdict is for an older snapshot;
   - `checks_failed` (exit 2) → a check exited non-zero, timed out, could not start or has an unknown exit code: the gate cannot be accepted whatever Jev said. Report the failing check; fix the code and start again from step 1, or end with `Incomplete:`;
   - `unavailable` (exit 3) → Jev could not evaluate some part (the runner already retried each call once, and reconnected once for the next part; parts it could not send, or all parts when there are no credentials or the server cannot start, are listed as `unevaluated`); `conditions` lists every operational condition, also one the outcome does not name (for example `unavailable` behind `checks_failed`); report **"Jev unavailable; gate not evaluated"** for them (never `auto`), with the real check results and the parts that were evaluated;
   - `escalate` or `ask_user` (exit 2) → stop and ask the user, quoting the numbers;
   - `needs_evidence` (exit 2: `review` caused only by missing evidence) → add the missing real evidence ids (hunks, excerpts, checks) to those claims;
   - `not_ready` / `invalid_input` (exit 4) → fix what `problems` lists with real material (a claim without evidence, an unknown id, an uncovered hunk, content the sanitizer had to remove, the work tree changing during the run, an empty diff), or report the gap and end with `Incomplete:`; never fill a gap with placeholders;
   - `accepted` (exit 0) → every part is `auto` and valid and every check passed, for this snapshot and these claims only. A later run on the same request and snapshot must keep every claim of the earlier runs (it may add evidence or claims, never drop one).
   A failed check stays a failure; it is not reinterpreted.
   **No re-runs for a better verdict.** Run the runner again only (a) once, with genuinely new real evidence for a `needs_evidence` result, or (b) after you fixed a failed check or the snapshot changed (a new snapshot needs a new gate). Never re-run for `review`, `ask_user` or `escalate` without such a change, and never to obtain a more favourable verdict.
   **`review` on correct claims is frequent (R6).** With the default upstream thresholds, `jev_gate` often answers `review` even when every claim is `verified` and the evidence is complete (a trivial correct fix measured `safe_to_apply` 0.59); `auto` needs `safe_to_apply` and the lowest rubric confidence at or above `auto_accept` (default 0.8) and the composite at or above `composite_floor` (default 0.7); below `review_at` (default 0.5) the part escalates, and anything in between is `review`. Report such a part as it is — "gate: review (not auto)" with its `safe_to_apply`, its reason codes and the claim verdicts and confidences — never as accepted and never as a contradiction; keep the thresholds as they are (do not lower them), and do not re-run. Completion is then not verified: end with `Incomplete:` or ask the user.
7. **Answer once**, after the whole report, with everything in one message: the change; the checks the runner ran with their exit codes (`exit: null` = unknown or timed out); the `outcome`, `verdict` and `status`; every part's result (action, reason codes, `safe_to_apply`) and every claim's overall verdict (`claims`: `contradicted` > `unevaluated` > `unsupported` > `verified` over its occurrences), or the fixed phrase; the coverage (`coverage`: planned, sent, evaluated, unavailable and unevaluated parts); the limits from `limits` (unattributed or pre-existing changes, unevaluated binaries/submodules, cut output, uncited hunks, redactions); and all remaining issues and questions together. When the report says `summary_truncated`, it was compacted to fit 8 KB without losing a part, a check, a limit or a claim verdict: the per-occurrence detail is dropped (`occurrences_omitted`), long limit lists become `{count: n}` and redactions are summed per kind, `claims` may become verdict → claim-number ranges (`{"verified": "1-12,14"}`), `parts` may become `[part, verdict|state, action, [reason_codes], safe_to_apply]` and `checks` `[n, exit, ...flags]`. When `limits.partitioned` is true, say so explicitly: each part judged its slice of the diff and its claims, and no single call evaluated the whole patch. If completion is not verified, end with a line starting with `Incomplete:`.

Completion counts only through the runner's signed receipt for this session, request and snapshot (`receipt` in the output); a result printed or pasted any other way is not evidence.
